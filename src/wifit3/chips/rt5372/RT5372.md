# RT5372 (RT5392)

A standalone clean-room port of the Ralink RT5372 (silicon `0x5392` "RT5392", USB `148f:5372`,
RF5372, 2T2R, 2.4 GHz only) from the rt2x00 kernel source. It mirrors the module shape of
`chips/rt3070/` but shares no code with it or with `chips/rt2800usb/` — it replaces the latter.

## Status

DEFAULT driver for `148f:5372`, grade A. Byte-perfect `verify_pcap` on all four captures; full
attack matrix green on PAU05 (deauth → handshake, PMKID, WEP ChopChop + ARP replay, WPS PIN + PBC);
30-min soak clean on PAU05 + PAU06; warm reattach works. `WIFIT3_RT5372=rt2800usb` opts back to the
old shared imitation for an A/B.

## Gotchas

**This driver is standalone because of an EFUSE word-vs-byte bug.** `rt2800_read_eeprom_efuse`
loops a u16-*word* index (0, 8, …, 248) into `EFUSE_CTRL_ADDRESS_IN`; the shared
`chips/rt2800usb/eeprom.py` passes a *byte* offset, so it reads from double the address on every
block past block 0. The MAC (offset 0) is coincidentally correct, which hid the bug. On RT5392 the
bug corrupts freq_offset (reads 30 vs the real 59), NIC_CONF0 (chain count), LNA and RSSI. The
clean-room reader uses the word index; `verify_pcap` catches the wrong one on block 1.

**2T2R, not 1T1R.** With the correct EFUSE read, `NIC_CONF0=0xff22` → txpath=rxpath=2. The
imitation's byte bug read `0x1a19` (rxpath=9), tripping its "unburned" heuristic that forced 1T1R —
a likely contributor to its weak RX. Running 2 chains plus the correct freq_offset is why the
clean-room port hears ~2× as many networks (62–68 vs 31 BSSIDs over a 13-channel sweep, same card).

**Warm = our monitor state, not just "inited".** `mac.is_chip_warm()` reads `PBF_SYS_CTRL` (cold
plug `0x2F80`, READY + pre-init bit 13; `usb_init_registers` clears bit 13) AND that `RX_FILTER_CFG`
still has `DROP_NOT_TO_ME` clear. Pre-init-clear alone only proves *some* driver inited it: the
Windows/kernel stack leaves the chip in managed mode (DROP_NOT_TO_ME set), and warm-reattaching onto
that skips `enable_monitor` so RX comes up deaf (the bug that made a fresh WinUSB install need a
replug). Our monitor init is the only thing that clears DROP_NOT_TO_ME, so that bit is the "we did
this" signal; anything else falls to cold init, which always works. `close()` never resets the radio,
so a real re-run still reads warm. Runtime-only; the cold-capture gate doesn't model it.

**Green ≠ correct.** The gate can't validate hardcoded or per-card values, so EFUSE must be read
dynamically and every branch ported. Two captured hardware units (PAU05, PAU06) are both silicon
`0x5392` and indistinguishable by USB ID; PAU05 is the weak unit (~3.6 beacons/s on the imitation),
PAU06 healthy (~7.8/s).

## EEPROM variants (RF-chip / antenna)

Ralink separates **two** ids: the **RT MAC silicon** (`MAC_CSR0` → `init_bbp`/`init_rfcsr`,
switched on `chip.rt`) and the **RF companion chip** (EEPROM → `config_channel`, switched on
`chip.rf`). For `148f:5372` the silicon is fixed **RT5392**, so `init_rfcsr_5392` + the
`init_bbp_53xx` RT5392 gates are correct for every admitted card. What varies is the EEPROM:

| field | source | reference (PAU05/06) | other admitted cards |
|-------|--------|----------------------|----------------------|
| RF chip | `EEPROM_CHIP_ID` (word0) | RF5372 | RF5370 / RF5390 / RF5392 (all → `config_channel_rf53xx`) |
| chain count | `NIC_CONF0.TX/RXPATH` | 2T2R | 1T1R |
| bt-coexist | `NIC_CONF1.BT_COEXIST` | 0 | 1 |

**RF is EEPROM-derived, not silicon-derived** — RT5390 and RT5392 silicon both read
`EEPROM_CHIP_ID`; RF5370 (1T1R) vs RF5372 (2T2R) differ *only* there. `eeprom.resolve_rf_chip`
is a 1:1 port of the RF-id block of `rt2800_init_eeprom` [SRC rt2800lib.c:11182-11235], logged at
connect (the `silicon=… rf=… NtNr … eeprom=burned/unburned` line). An unrecognised/erased
`EEPROM_CHIP_ID` is NOT `-ENODEV`'d (as the kernel would) — it runs the silicon-default rf53xx
tune with an `untested variant:` warning, so a blank-EFUSE dongle still comes up.

**Chain count is fully runtime.** `config_ant`, `disable_unused_dac_adc`, `normal_mode_setup_5xxx`,
and the `TX_PIN_CFG` PA/LNA switches all branch on `NIC_CONF0.TX/RXPATH`; the 1T1R arms were
already ported. The `config_channel_rf53xx` RFCSR50 / RFCSR1_RX1_PD writes gate on **RT5392
silicon** (matching the kernel), so a 1T1R RT5392 card still takes them.

**bt-coexist is now ported, not fail-loud.** `config_channel_rf53xx` picks RFCSR59 from `RF59_BT`
vs `RF59_NON_BT` by `ev.bt_coexist` (was a `NotImplementedError`); RT5392 skips the RT5390F+
rev-gated `r55/r59_*_rev` arms. Reference (bt=0) is byte-identical.

**Residuals (need a burned non-reference unit to verify):** the RFCSR50/RFCSR1_RX1 and RF59_BT
branches are traced 1:1 from source but unexercised on captured hardware (all captures are RF5372
2T2R, bt=0). TX-power *values* (`txmixer_gain_24g`, `EEPROM_TXPOWER_BYRATE`) are unchanged here —
RX-unaffected, out of scope for this generalization.

## Orientation

Kernel C is the spec (`driver_sources/rt2x00-source-v6.18/{rt2800lib.c,rt2800usb.c,rt2x00usb.c}`),
translated line by line; the cold-boot capture is ground truth where source and wire disagree. Never
read `chips/rt2800usb/` — it's the imitation this replaces and carries the EFUSE bug above.

Bring-up follows the kernel order: `probe_rt` → EFUSE read → firmware (`rt2870.bin` at offset 4096,
4 KB) → `init_registers` → `init_bbp_53xx` → `init_rfcsr_5392` → `start_queue_rx` → monitor entry.
Channel tune is `config_channel_rf53xx` (ch 1–14, 20 MHz). RX decode is `rx.py`, TX descriptor build
is `tx.py`. Names match the kernel functions; grep the source tree to cross-reference.

## Debug log

### 2026 — clean-room bring-up

Ported from the kernel in milestones, gated by `verify_pcap` at each step: scaffold + word-offset
EFUSE + GPIO, then firmware + radio prologue + `init_registers`, then `init_bbp_53xx` +
`init_rfcsr_5392` + `start_queue_rx`, then channel tune + monitor entry + link_tuner (full
single-cursor PASS: capture-1 5060/5060, -2 5020/5020, -3 5023/5023; only the aireplay TX_STA_FIFO
polls waived), then RX + driver + the `WIFIT3_RT5372` A/B, then the TX descriptor (byte-matches the
kernel's captured deauth, live-confirmed on PAU05).

The "terrible ~4.0/s" early reading was the weak PAU05 unit, now resolved on the clean-room driver:
PAU05 passes the full attack matrix and a 30-min soak, and a cold replug reads the nearby AP at
mean ~8/s (8–10/s healthy bar). RX A/B on PAU06 over a 13-channel sweep: clean-room hears 62–68
BSSIDs / ~920–1056 frames per window vs the imitation's 31 / ~576, both flat over 3 min — the 2T2R
bring-up + correct freq_offset=59 vs the imitation's byte-bug-forced 1T1R + under-driven AGC. On a
single strong AP the two tie (~7/s — that AP saturates either receiver); the difference is breadth.
Warm reattach measured ~8.7/s vs cold ~8.5/s on PAU06 (steadier, stdev 1.2), skipping ~1200 init
ops and avoiding the RX dip a cold re-init on a warm chip showed.
