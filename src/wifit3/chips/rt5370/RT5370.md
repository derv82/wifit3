# RT5370 (RT5390)

A standalone clean-room port of the Ralink RT5370 (silicon `0x5390` "RT5390", rev `0x0502`
"REV_RT5390F", USB `148f:5370`, RF5370, **1T1R**, 2.4 GHz only) from the rt2x00 kernel source. It
mirrors the module shape of the 2T2R sibling `chips/rt5372/` (RT5392) but shares no code with it or
with `chips/rt2800usb/`. The kernel drives both RT5390 and RT5392 through the same `rt2800usb`
driver, branching on chip id; this port carries those branches and exercises the RT5390 ones.

## Status

Cold bring-up **byte-perfect** under `verify_pcap` on all three captures (capture-1 7552/7552,
-2 7528/7528, -3 7623/7623 ops; only the aireplay TX_STA_FIFO polls waived). Covers probe → EFUSE →
firmware → MAC/BBP/RFCSR init → monitor entry → the full 1–14 channel sweep → the captured aireplay
deauth. The TX descriptor `tx.py` builds **byte-matches** the captured aireplay deauth both
directions (TXINFO + TXWI + frame); the only per-frame differences are the seqctl (the running
sequence number) and TXWI_W1 PACKETID_ENTRY — the kernel's TX-status ring token `(entry_idx % 3)+1`
[SRC rt2800lib.c:839], not part of the over-air frame. Hardware RX is healthy: a 60 s cold soak on
the reference AP reads mean **7.8 beacons/s** (median 8, max 10, stdev 1.3, zero dropout seconds) —
~80% of the ~9.8/s single-AP ceiling, in the 8–10/s healthy band for a 1T1R card. **The attack
matrix (deauth → handshake, PMKID, WEP, WPS) needs live TX and is the user's gate — not yet run.**

## Gotchas

**This card is exactly REV_RT5390F (rev `0x0502`).** Every `rt2x00_rt_rev_gte(RT5390, REV_RT5390F)`
branch takes the F arm:
- `init_rfcsr_5390` (rfcsr.py): RFCSR 6=0xe0, 25=0x80, 46=0x73, 53=0x00, 56=0x42, 61=0xd1.
- `config_channel_rf53xx` (chan.py) non-BT tail: writes **both** RFCSR55 (`RF55_NON_BT_REV`) and
  RFCSR59 (`RF59_NON_BT_REV`) — not the single-RFCSR59 path the RT5392 / pre-F RT5390 takes. This
  is the one channel-tune divergence from the rt5372 port; getting it from the C (not the sibling)
  is the whole point.
The pre-F arms are ported behind their real rev check but `#TODO untestable` here.

**1T1R, RF5370.** NIC_CONF0 reads txpath=rxpath=1 (read dynamically, never hardcoded). The
RT5392-only writes are skipped: RFCSR50 (chain-2 TX power) + RFCSR1 RX1/TX1_PD in the tune,
BBP88/95/98/134/135 in `init_bbp_53xx`. `init_bbp_53xx`'s hardware-RX-antenna-diversity block is
gated off (rev `0x0502` < REV_RT5390R/RT5370G).

**Standalone because of an EFUSE word-vs-byte bug** (shared with rt5372). `rt2800_read_eeprom_efuse`
loops a u16-*word* index (0, 8, …, 248) into `EFUSE_CTRL_ADDRESS_IN`; the shared
`chips/rt2800usb/eeprom.py` passes a *byte* offset and reads from double the address past block 0.
The clean-room reader uses the word index; `verify_pcap` catches the wrong one on block 1. On this
card the correct read gives freq_offset=43, RF5370, 1T1R.

**One RF_CSR_CFG busy poll records an empty completion.** capture-1 and capture-3 each contain a
single `RF_CSR_CFG` (0x500) regbusy read whose first, still-busy iteration carries no response bytes
on the wire (capture-2 has none). `regbusy_read` treats a short (<4-byte) read as "can't prove
busy=0, keep polling" — mirroring the kernel only exiting on a positive busy-clear read — so it
consumes the empty op and reads the real (not-busy) value on the next poll, exactly as the kernel
did. Collapsing the empty read to 0 would falsely read "not busy" and skip the second poll.

**Warm = READY-set + pre-init-clear.** `mac.is_chip_warm()` reads `PBF_SYS_CTRL`: cold plug reads
`0x2F80` (READY + pre-init bit 13); `usb_init_registers` clears bit 13, so a re-plug seeing
READY-set-but-bit13-clear means we inited it (`close()` disposes the USB handle but never resets the
radio). Warm skips FW upload + all MAC/BBP/RFCSR init + `enable_monitor`. Runtime-only, not in the
kernel cold sequence, so the cold-capture gate doesn't model it and stays green.

**Monitor-mode link tuner (BBP66 AGC).** The kernel runs `rt2800_link_tuner` only for STA/AP vifs,
so in monitor BBP66 is pinned to the per-tune default and a very-close AP compresses the front-end —
measured: a −36 dBm AP on ch9 self-strangled to ~4 bcn/s, recovering to ~9.8/s (the wire ceiling) as
BBP66 was backed off. `driver.py` runs the kernel's own heuristic (`+0x10` when the RX RSSI EWMA
beats −80 dBm) on a ~1 Hz async task: the close AP recovers to ~7.1/s with breadth kept (the other
ch9 APs still heard), and an already-healthy AP is untouched (ch1 reference 7.8→7.9/s). Runtime-only
(no link-tuner writes in the kernel's monitor capture), so `verify_pcap` doesn't model it and stays
green. Focus-target steering (drive the AGC off one BSSID's RSSI) is parked for a separate design.

## Orientation

Kernel C is the spec (`driver_sources/rt2x00-source-v6.18/{rt2800lib.c,rt2800usb.c,rt2x00usb.c}`),
translated line by line; the cold-boot capture is ground truth where source and wire disagree. Never
read `chips/rt2800usb/` — it's the imitation with the EFUSE bug above. The rt5372 sibling's
`init_bbp_53xx`/`config_channel_rf53xx` are the *same* shared kernel functions, but every
RT5390-specific value here is ported fresh from the C.

Bring-up follows the kernel order: `probe_rt` → EFUSE read → firmware (`rt2870.bin` at offset 4096,
4 KB) → `init_registers` → `init_bbp_53xx` → `init_rfcsr_5390` → `start_queue_rx` → monitor entry.
Channel tune is `config_channel_rf53xx` (ch 1–14, 20 MHz). RX decode is `rx.py`, TX descriptor build
is `tx.py`. Names match the kernel functions; grep the source tree to cross-reference.

## Scripts

- `scripts/verify_pcap.py rt5370 [capture-1|-2|-3]` — the cold-boot byte gate; single monotonic cursor.

Captures: `driver_captures/captures_rt2800usb_rt5370/capture-1..3.pcap` (cold boot, rt2800usb v2.3.0,
kernel 6.18.12+kali; ~7.5k vendor ops each, including the aireplay --test + -0 deauth tail).

## Debug log

### 2026-07-11 — generalize across EEPROM burns (any 148f:5370)

Ported `rt2800_init_eeprom`'s RF-chip resolution [SRC rt2800lib.c:11187-11201] as
`eeprom.resolve_rf_chip(silicon_rt, ev)` — RT5390/RT5392 silicon take the RF id from
`EEPROM_CHIP_ID`, not the (garbage-on-RT53xx) NIC_CONF0.RF_TYPE nibble; the reference reads
0xf there. `connect()` now logs the full runtime config (silicon/rev, rf name, `%dT%dR`,
ext-LNA, bt-coex, ant-div, freq-off, burned/unburned) and warns `untested variant` for an
RF outside the ported rf53xx set (RF5370/5372/5390/5392) — best-effort, no `-ENODEV`.
Removed the last fail-loud path: `config_channel_rf53xx` raised `NotImplementedError` on
`bt_coexist`; now it writes the BT-combo r55/r59 tables (rev-F → RFCSR55+59, pre-F →
RFCSR59) [SRC rt2800lib.c:3431-3450], runtime-gated on NIC_CONF1 BT_COEXIST. `_config_tx_pin_pa`
now takes the BT flag faithfully (PA_PE_G0_EN forced on for a combo card — identical to the
non-BT value on 2.4 GHz, so the reference wire is unchanged). Chain count was already
runtime (NIC_CONF0 TX/RXPATH → config_ant/TX_PIN/BBP138). `verify_pcap` all three captures
still byte-identical (7552/7528/7623); the RT5392-silicon chain-2 writes (RFCSR50, RFCSR1
RX1/TX1_PD, BBP88/95/98/134/135) stay **silicon**-gated per the kernel — a 2T2R EEPROM on
RT5390 silicon skips them exactly as the kernel does. Residual/deferred: init_rfcsr is
hardcoded to `_5390` (silicon dispatch); an RT5392-**silicon** 148f:5370 (unheard of — that
SKU is 148f:5372, the rt5372 sibling) would need `init_rfcsr_5392`, out of scope. RF5592 →
rf55xx tune unported (logs untested-variant, runs rf53xx). Live TX still the user's gate.

### 2026-06-24 — clean-room bring-up

Ported from the kernel by copying the rt5372 module shape and surgically re-deriving the
RT5390/1T1R/rev-F specifics from `rt2800lib.c`: chip id 0x5390, `init_rfcsr_5390` (new table + the
REV_RT5390F branches), `config_channel_rf53xx`'s rev-F RFCSR55+59 `_rev` tables, and the 1T1R
chain config (skips RFCSR50 / BBP88·95·98·134·135). `verify_pcap` single-cursor PASS on all three
captures end to end; the only wire fix was `regbusy_read`'s short-read handling (the empty-completion
busy poll above). TX descriptor byte-matches the captured aireplay deauth (both directions).

Hardware RX confirmed on a cold replug: `beacon_watch --channel 1 --duration 60` on the reference AP
reads mean 7.8/s (median 8, max 10, stdev 1.3, no zero seconds) — healthy for 1T1R. A warm reattach
(prior session left the chip inited but not in monitor) reads nothing until a cold replug restores
the `enable_monitor` path; the cold run is the valid RX measurement. 2.4 GHz only (no 5 GHz radio).
Live-TX attacks remain the user's gate.

A user-reported weak spot — an ASUS AP "right next to me" (ch9, −36 dBm) reading only 3–5 bcn/s while
a less-close AP held 8–10 — turned out to be front-end overload. A BBP66 sweep on ch9 confirmed it:
the AP recovered monotonically 4.0 → 9.7/s as gain backed off (default 0x2c → 0x5c), at the cost of
breadth past +0x18. Added the kernel-faithful monitor-mode link tuner (+0x10 above −80 dBm, all-frames
EWMA): the ASUS recovers to ~7.1/s with the other ch9 APs still heard, ch1 reference unchanged at
7.9/s. `scripts/rt5370/agc_sweep.py` is the sweep harness.
