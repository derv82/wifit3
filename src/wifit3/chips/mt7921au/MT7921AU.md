# MT7921AU Protocol Notes

Verified ground truth for the MT7921AU (MediaTek chip `0x7961`). **Only confirmed
facts live here** — decoded from the cold-boot usbmon captures and checked against the
kernel source. Anything not in this file is a hypothesis until verified and added.

- Captures: `usb_dumps_new/captures_mt7921u_{pau0f,axml}-no-adapter-scatter/` — cold
  boot, captured with `disable_usb_sg=1` so the device→host (RX) half is recorded
  (MCU responses, the boot signal, 802.11 frames). `capture-3` is a clean cold boot.
- Kernel source: `data_dumps/mt76-source-v6.18/` (matches Kali 6.18.12's `mt7921u.ko`).
- Offline gate: `scripts/mt7921au/verify_pcap.py` (see below). Run after every change.

## Active Monitor / auto-ACK — NOT implemented

`FAKE_MAC = UNIMPLEMENTED`. The radio does **not** HW-ACK frames addressed to a programmed
MAC in our monitor path — HW-verified: WPS holds at ~120 EAPOL whether we arm a forged MAC
*or the card's real silicon MAC* (an ACKing card sits at ~15–25). So WPS/EAP/EvilTwin
retry-storm and time out; wifite warns ("not implemented — expect timeouts") and runs anyway.

- **Not our omission** — the mainline `mt7921u` we ported from doesn't ACK either; active
  monitor is broken across the whole mt76 family bar `mt76x0u`. Corroborated by
  [openwrt/mt76#839](https://github.com/openwrt/mt76/issues/839) and
  [morrownr/USB-WiFi#107](https://github.com/morrownr/USB-WiFi/issues/107).
- **Not `NONE`** — the silicon may be capable (connac2 has a programmable RMAC MUAR). Fix path:
  port the untried `REPT_MUAR`/`MUAR_UPDATE` MCU command (we only send the DEV_INFO omac), or
  wait for a fixed upstream to port from. Neither is proven possible yet.

## Hardware / USB

- chip `0x7961`, HW/SW version `0x8a108a10`. Both units enumerate as USB `0e8d:7961`.
- PAU0F: a single vendor-specific (class `0xFF`) interface — **if0**.
- AXML: a composite device (+Bluetooth); its WiFi function is the class-`0xFF`
  interface — **if3**. The driver auto-detects the `0xFF` interface; never hardcode it.
- Endpoints on that interface (identical on both units):

  | EP | dir | role |
  |----|-----|------|
  | `0x08` | OUT bulk | MCU commands |
  | `0x04` | OUT bulk | FW_SCATTER firmware chunks + 802.11 TX |
  | `0x05`/`0x06`/`0x07`/`0x09` | OUT bulk | AC queues / HCCA |
  | `0x84` | IN bulk | 802.11 RX **and** MCU responses (kernel routes responses here via `RXEVT_EP4_EN`) |
  | `0x85` | IN bulk | MCU responses when `RXEVT_EP4_EN` is clear |
  | `0x86` | IN intr | unused (no traffic in any capture) |

- **USB speed**: cold boot works on HighSpeed and SuperSpeed. Passive USB-3→USB-2
  adapters often still negotiate SuperSpeed — confirm with `probe_pau0f.py`.
- **No userland cold reset on Windows**: once firmware is running, `dev.reset()` does
  not re-cold-boot the chip (it re-acquires at the same bus address, still running). A
  physical replug is the only way to force a fresh cold boot.

## Firmware blobs

`assets/` holds the `_1_` variant: `WIFI_MT7961_patch_mcu_1_2_hdr.bin` +
`WIFI_RAM_CODE_MT7961_1.bin`, sha256-verified against Kali 6.18.12's linux-firmware.
USB `0e8d:7961` always uses the `_1_` variant.

- Patch header `mt76_connac2_patch_hdr` (BE): `n_region` at offset 44; sections are
  `mt76_connac2_patch_sec` (64 B, BE) — `offs`@4, `addr`@12, `len`@16.
- RAM trailer `mt76_connac2_fw_trailer` (36 B, at end of file): `n_region`@2; regions
  are `mt76_connac2_fw_region` (40 B, LE) before the trailer — `addr`@16, `len`@20,
  `feature_set`@24 (`OVERRIDE_ADDR`=BIT5, `NON_DL`=BIT6).

## MCU command wire format (verified byte-for-byte — gated by verify_pcap)

On EP `0x08`: `[4B SDIO hdr][64B mt76_connac2_mcu_txd][payload][pad → 4B align + 4]`.

- SDIO hdr (LE u32) = `tx_bytes` = `64 + payload_len`.
- `txd[0]` = `0x41000000 | skb_len`; `txd[1]` = `0x80010000`; `txd[2..7]` = 0.
- mcu_txd fields, by frame offset: `len`@36 = `32 + payload_len`; `pq_id`@38 = `0x8000`;
  `cid`@40; `pkt_type`@41 = `0xA0`; `set_query`@42 (`MCU_Q_NA`=3 for plain commands);
  `seq`@43; `ext_cid`@45.
- `DL_MODE_NEED_RSP` = `BIT(31)` — set in the PATCH_START / TARGET_ADDRESS_LEN payloads.
- FW_SCATTER short-circuits the txd: `[4B SDIO hdr][chunk][pad]`, 4096 B payload/chunk.

(Exact register addresses and constants are in `constants.py`; treat that as the
source of truth for values, this doc for structure.)

## MCU response wire format (on EP `0x84`)

`mt76_connac2_mcu_rxd`: `rxd[6]` (24 B) then `len`@24, `pkt_type`@26, `eid`@28, `seq`@29,
`option`@30, `ext_eid`@32. **The device echoes the command's `seq` in its response**, so
responses are matched to commands by seq.

## Boot sequence (this is the part that matters)

1. **MCU power-on**: vendor write (`bRequest` `MT_VEND_POWER_ON`=0x04, `wIndex`=1), then
   poll `MT_CONN_ON_MISC` (`0x7c0600f0`) BIT0.
2. **Post the IN-URB drainer** on EP `0x84`/`0x85` *before* `dma_init` (kernel order:
   `mt76u_alloc_queues` precedes `mt792xu_dma_init`; `GLO_CFG`'s `RX_DMA_EN` backs up if
   no RX URBs are queued).
3. **`dma_init`** — the WFDMA register init (prefetch → GLO_CFG → DMASHDL → WLCFG →
   rx_evt_ep4 → epctl_rst_opt). Every write is verified byte-for-byte against the
   capture by `verify_pcap` CHECK 1.
4. `MT_SWDEF_MODE` = 0 (normal), then `MT_UDMA_TX_QSEL` = `FW_DL_EN`.
5. **Firmware load — STRICTLY LOCKSTEP.** Send one MCU command, wait for its ack on EP
   `0x84` (seq-matched), then proceed. FW_SCATTER chunks go on EP `0x04` between commands.

   | command (cid) | ack `eid` |
   |---|---|
   | PATCH_SEM_GET (0x10) | `0x04`, `ext_eid` 0x02 = NOT_DL_SEM_SUCCESS |
   | PATCH_START_REQ (0x05) | `0x01` |
   | PATCH_FINISH_REQ (0x07) | `0x01` (after the CRC pass) |
   | PATCH_SEM_RELEASE (0x10) | `0x04`, `ext_eid` 0x03 = REL_SEM_SUCCESS — **~250 ms later** |
   | TARGET_ADDRESS_LEN_REQ (0x01) ×4 | `0x01` each; the ack **precedes** that region's chunks |
   | FW_START_REQ (0x02) | `0x01` = **MCU_EVENT_FW_START**, ~15 ms later — the boot signal |

   The lockstep is mandatory. If commands outrun the chip, it acks the patch session,
   goes silent for the entire RAM phase, and FW_START hits an uninitialized chip and
   wedges (EP0 dies). The same wait fixes the SuperSpeed first-chunk short-write: the
   chip needs the post-PATCH_START setup window before it can sink bulk data.
6. **Boot signal** = the `MCU_EVENT_FW_START` (eid 0x01) response to FW_START.
   `FW_N9_RDY` (`MT_CONN_ON_MISC` bits 1:0 = `0x3`, read over EP0) is a best-effort
   secondary confirmation — EP0 can briefly lag right after the handoff.

## Warm re-attach — light reattach to running firmware (HW-validated, repeatable)

A warm chip (firmware still running from a prior wifit3 run) is **reattached, not
rebooted** — the kernel `mt7921u_resume` model. `driver.connect()` reads
`MT_CONN_ON_MISC`/`FW_N9_RDY` (the same warm check `mt7921u_probe` does — reading it is
HW-safe here), and on a warm chip calls `_warm_reattach`:

- gate a light `dma_init(resume=True)` on `mt792x_dma_need_reinit` (the `MT_WFDMA_NEED_REINIT`
  latch; a normal reconnect leaves it set, so this is skipped),
- re-post RX (start the reader) — `mt76u_resume_rx`,
- re-sync the channel.

No `wfsys_reset`, no `mcu_power_on`, no firmware reload, no post-boot init — the firmware
already did all that and resumes streaming RX the instant a read is posted. **HW-validated
2026-06-12: cold boot → close → warm reattach in ~5 ms, 400-500 frames/3 s window, and
REPEATABLE across back-to-back runs with no replug** (the case that broke every earlier
approach). `is_warm` reflects the path taken (True = reattached, False = cold boot).

**`set_hif_suspend(false)` is intentionally omitted** — a justified exception. The kernel
sends it on PM resume because IT called `set_hif_suspend(true)` on suspend; our cross-process
reconnect never suspended the HIF (RX streams immediately), so there is nothing to un-suspend.
The kernel has no analog for a fresh-handle reconnect to never-suspended firmware.

### What the dead end taught us — do NOT re-try the reset approach
The long 2026-06-12 detour tried to **cold-boot a warm chip** (`wfsys_reset` + re-acquire +
`load_firmware`). That POISONS a warm chip on WinUSB: the `Errno 32` bulk-pipe stall is caused
by the **`wfsys_reset` / `mcu_power_on`** cold-boot ops fired at a still-running chip — NOT (as
first assumed) by reading the warm bit. HW-verified: reading `MT_CONN_ON_MISC` leaves RX
streaming untouched. The kernel's PROBE path can reset endpoint state with `usb_reset_device`
(a real port reset) *before* the warm `wfsys_reset`; libusbK's `dev.reset()` is a no-op on this
single-node composite device (`USB\VID_0E8D&PID_7961\000000000` — Zadig bound the whole device,
BT interfaces included, under one libusbK node), so we can't replicate PROBE on WinUSB. But we
don't need to: RESUME (light reattach) needs none of it. The single "426-frame" success from the
reset approach was a non-reproducible fluke (bisected with zero driver code → stalls on a
clean-warm chip). Evidence the light path works: `scripts/mt7921au/warm_c_attach.py` (reattaches,
streams RX, and drives `set_channel` on a warm chip with no boot).

The single-function PAU0F drops to cold on its own when idle, so it is rarely warm between runs;
when it is, the same light reattach applies.

## verify_pcap — the offline byte-for-byte gate (Pcap Replay)

`scripts/mt7921au/verify_pcap.py` runs the driver's real code against the cold-boot
scatter capture (auto-detecting the mt7921 device address):
- **CHECK 1** — `dma_init` register writes, byte-for-byte.
- **CHECK 2** — every firmware-load MCU command rebuilt via the real `_build_mcu_frame`
  and paired with its captured device response (through the MCU_EVENT_FW_START signal).
- **CHECK 3** — the full post-boot stream on one cursor: the deterministic init
  (`post_boot_init`, 177 ops through `add_interface`) **then** the operational tail
  (`walk_operational`) — monitor entry, the 65 airodump channel hops, and the periodic
  `mt792x_mac_work` MIB cycles (`update_survey` every tick, `update_mib_stats` every
  second), all interleaved in the tool's wire order. **Full PASS: all 6103 post-boot
  ops reproduced byte-for-byte.**
- **CHECK 4** — TX descriptor accuracy: every captured aireplay TX frame (the `-0`
  deauth + auth on EP 0x09, the `--test` null frames on EP 0x04) rebuilt via the real
  `tx.build_tx` and asserted byte-for-byte incl. the chosen endpoint. **PASS: 221 TX
  frames** (128 deauth / 30 auth / 33 probe_req / 30 null) on all 6 scatter captures.

Only `*-scatter` captures (`disable_usb_sg=1`, which records the device→host RX) are
valid targets — they verify the firmware handshake (CHECK 2) and the post-boot
command/response stream (CHECK 3). The gate **refuses** a pre-scatter capture (no RX):
the register-only CHECK 1/4 would pass on it, but that is not verification of the part
that matters, so it aborts rather than print a hollow PASS. (CHECK 4 SKIPs if a scatter
capture stopped before the aireplay phase — boot + RX are still fully verified.) Helpers:
`analyze_usb_traffic.py` (per-endpoint RX/TX tally), `decode_fw_handoff.py` (FW_START
timeline + per-command response decode).

## Post-Port Checklist (`planning/PORTING.md`) — agent items 1-6

1. **Waivers** — pau0f scatter captures reproduce with **zero** waivers (CHECK 1-4). The
   AXML adds exactly one: a btusb boot-status poll (`0x00300000`), i.e. a *different
   driver's* traffic on the composite WiFi+BT device — the only legitimate waiver kind.
2. **Skip audit** — `mac_init` matches the kernel leaf-for-leaf; the gate verifies every
   init/operational wire op. Non-wire findings: the driver was missing the `mac_address`
   and `is_warm` `WlanDriver` protocol attributes (now added — `is_warm` is always False
   since warm reattach is unsupported; `mac_address` is parsed on cold boot from the
   GET_NIC_CAPAB reply's `MT_NIC_CAP_MAC_ADDR` TLV — `mcu.parse_nic_capability` — and is
   None only on a warm reattach, which skips post-boot init). Deliberate, marked
   simplifications: world `'00'` regdomain (`regdomain.py`), 2×2 antenna mask `0x3`
   (`mcu.py`, `BIT(nss)-1` for the fixed 2×2 7961), EFUSE handled firmware-side via
   `set_eeprom` (no host parse).
3. **Capture coverage** — all 6 `*-scatter` captures PASS full CHECK 1-4; non-scatter
   captures are refused (no RX to verify against).
4. **TX byte-diff** — CHECK 4 (221 frames) + live deauth HW-confirmed.
5. **Async producers** — mt7921's only periodic register-writer is `mt792x_mac_work` (MIB
   survey poll; gate-reproduced; the userland monitor driver doesn't schedule it — reads +
   a benign RXTIME clear). The other `INIT_DELAYED_WORK`/`INIT_WORK` are STA/power-save/
   scan/error-recovery paths that don't fire in monitor. **No host-side DIG/IGI/AGC loop —
   the PHY/AGC live in firmware** (unlike rtw88), so there is no periodic gain re-seed to
   port; the green gate proves no periodic writer is missing from the operational window.
6. **Recal cadence** — the monitor channel tune is a single `config_sniffer` UNI command
   (CHECK 3 verifies all 65 captured hops); the firmware does the per-tune RF recal
   internally, and a cancelled hop can't leave a half-tuned RF state (one atomic command).
   No periodic host recal (see 5).

7. **Break-it (human)** — HW-validated on the PAU0F (2026-06-12): WEP stays WEP (no
   spurious flip), ChopChop works, ARP-replay sustains ~350 IVs/s (WEP key cracked in
   ~60 s), WPS-PBC succeeds, PMKID works, deauth→handshake works. Two bugs this surfaced,
   now fixed: (a) RX delivered the whole USB buffer instead of `data[mpdu_off:MT_RXD0_LENGTH]`
   — the trailing alignment padding let the beacon IE walk over-read (stray RSN → WEP AP
   stuck at WPA2) and corrupted WEP-ICV/WPS-HMAC/frag length math; (b) injected frames
   reused seq 0 (the chip transmits the TXD SN_VALID seq, no auto-assign) so APs deduped
   interactive attacks — `inject_frame` now stamps an incrementing frag-preserving
   `seq_ctrl` (`tx.stamp_seq_ctrl`). Known remaining gap: the A-MSDU / `hdr_trans`
   data-frame RX path isn't reconstructed (doesn't affect the working attack suite).

## 5 GHz inject investigation — rate path correct, bug is RF-side (2026-06-21)

**Symptom** (user, vs an AC66U 5 GHz AP; `planning/BUGS.md`): WPS-PBC + PMKID fail on
5 GHz but work on 2.4 GHz; 5 GHz **RX** is fine — so our injected frames never land on the
AP. BUGS.md named `tx._tx_rate_val`'s `band_5ghz` branch the prime suspect.

**The rate path is correct — ruled out.** Audited leaf-for-leaf against
`mt76_connac2_mac_tx_rate_val` (`mt76_connac_mac.c:296`) for a monitor (no-conf) inject:

- **The band flag reaches.** `driver.inject_frame` passes `band_5ghz=self._channel > 14`
  (`driver.py:192`); `self._channel` is updated by every `set_channel`. Not a stale-flag bug.
- **The rate value is right.** Kernel 5 GHz path: `offset = 4` → `mt76_rates[4]` =
  `OFDM_RATE(11, 60)` (`mac80211.c:165`), `hw_value = 0x10b` → `idx = 0x10b & 0xff = 11`,
  `mode = 0x10b >> 8 = 1` (OFDM). `_tx_rate_val(True)` produces exactly that:
  `FIELD_PREP(MT_TX_RATE_IDX, 11) | FIELD_PREP(MT_TX_RATE_MODE, 1) = 0x4b` (masks
  `GENMASK(5,0)` / `GENMASK(9,6)`, `mt76_connac2_mac.h:139,135`). The OFDM `_idx` of 11 is
  the *HW PLCP rate index* for 6 Mbps, not a 0-based table slot — which is why `| 11` is
  correct, not a typo.
- **The FIXED_RATE TXD block is 1:1 with the kernel** (`mt76_connac_mac.c:593`): `txwi[2] |=
  HTC_VLD`, `txwi[6] = FIXED_BW | TX_RATE(rate)`, `txwi[3] |= BA_DISABLE`. `MT_TXD6_TX_RATE`
  is the **only** band-dependent TXD field, so the 5 GHz TXD is byte-identical to the
  byte-verified 2.4 GHz TXD (CHECK 4, 221 frames) except this (correct) rate.

**So the failure is outside the TX descriptor.** RX tunes (CH36/44/149/157 return beacons),
the bytes are right, yet the AP never hears us. Leading suspect: **5 GHz TX power /
per-channel TX cal.** The monitor channel-switch is a single `config_sniffer` UNI command
(`mcu.config_sniffer`); the kernel's full channel switch also programs TX power, and the
firmware-internal per-tune recal may leave 5 GHz output at a default adequate on 2.4 GHz
(inject verified there) but too weak on 5 GHz. **Not a clear source fix** — the port logic
matches the capture — so no blind change was made.

**Next steps:** capture a 5 GHz aireplay session with the new per-band capture flags
(`capture.py --bssid5g/--channel5g/--client5g`) and byte-diff the driver's 5 GHz inject —
this analysis predicts a MATCH, which would confirm the TXD is fine and point firmly at
RF/TX-power. Then check whether the sniffer channel-switch needs an explicit 5 GHz TX-power
program (the connac `SET_RATE_TX_POWER` path) that the monitor port currently omits.
