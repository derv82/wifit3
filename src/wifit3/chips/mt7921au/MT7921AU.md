# MT7921AU (mt7921au)

A port of the MediaTek `mt76`/`mt7921u` kernel driver. MT7961 silicon (chip `0x7961`,
USB `0e8d:7961`): 2×2 2.4 + 5 GHz 802.11ax, connac2, firmware-based — the PHY/AGC live in
firmware, so there is no host-side DIG/IGI/AGC loop to port.

## Status

Cold firmware boot works on Windows userland on both units (Panda PAU0F, ALFA AWUS036AXML)
and both USB-2 HighSpeed and USB-3 SuperSpeed. Monitor RX works on both bands (2.4 GHz CH1
~375 beacons/3 s; 5 GHz CH36/44/149/157 all 100+/3 s). Warm reattach works and is repeatable.
Linux (Kali VM) is validated too: after device setup + a replug, cold boot + post-boot init +
monitor RX pass on both bands (2.4 GHz CH1 ~350 frames/3 s; 5 GHz CH36/44/149/157 ~1100 frames
total). Device setup sets `LINUX_REPLUG_AFTER_MODPROBE` — the udev rule + modprobe blocklist only
apply on the next device-add, so a replug is required before our cold boot can claim the card.
TX works: `tx.build_tx` is byte-verified against all 221 captured aireplay frames, and the full
attack suite (deauth, WEP ChopChop, WEP ARP-replay ~350 IVs/s, WPS-PBC, PMKID) is HW-validated
on the PAU0F on 2.4 GHz, with WEP APs staying WEP. `verify_pcap` is a full PASS (all 6103
post-boot ops, all 6 scatter captures).

Broken/weak: WPS stays chatty and fragile on both bands — no HW-ACK (active monitor /
auto-ACK is unimplemented, see Gotchas). 5 GHz inject is suspected RF-side weak (see Gotchas).

Untested: AXML live attack test, a fuller warm-boot survey, and the A-MSDU / `hdr_trans`
data-frame RX path (not reconstructed — doesn't affect the working attack suite).

## Gotchas

**Auto-ACK / active monitor is unimplemented, and we don't know if the silicon can do it.**
`FAKE_MAC` is unimplemented, so WPS/EAP run un-ACKed (wifite warns about timeouts). One WPS PBC
exchange logs ~120 EAPOL frames here vs ~15-25 on a card whose auto-ACK works. Upstream issues
(openwrt/mt76#839, morrownr/USB-WiFi#107) report mt7921u lacks active-monitor support; ZerBea
notes PMKID capture depends on the device ACKing frames to its MAC. Hence "unimplemented", not
"none" — we never established whether the silicon *can* ACK.

**5 GHz inject likely fails RF-side, not in the TXD.** WPS-PBC + PMKID fail on 5 GHz but work on
2.4 GHz, while 5 GHz RX is fine — our frames never land on the AP. The rate path was audited
leaf-for-leaf against `mt76_connac2_mac_tx_rate_val` and is correct (band flag reaches via
`driver.inject_frame`'s `band_5ghz=self._channel > 14`; `_tx_rate_val(True)` yields `0x4b`, the
HW PLCP OFDM 6 Mbps rate; `MT_TXD6_TX_RATE` is the only band-dependent TXD field, so the 5 GHz
TXD is byte-identical to the verified 2.4 GHz one bar the correct rate). Leading suspect is
5 GHz TX power / per-channel cal: the monitor channel-switch is a single `config_sniffer` UNI
command, while the kernel's full switch also programs TX power, so the firmware-internal recal
may leave 5 GHz output too weak. Not a clear source fix — the port matches the capture — so no
blind change was made.

**The AXML is a composite device — never hardcode the interface.** PAU0F is a single
vendor-specific (class `0xFF`) interface (if0); the AXML adds Bluetooth and its WiFi function is
the class-`0xFF` interface (if3). The driver auto-detects the `0xFF` interface. Endpoints are
identical on both: EP `0x08` OUT = MCU commands, `0x04` OUT = firmware chunks + data TX, `0x09`
OUT = HCCA (mgmt/ctrl inject), `0x84` IN = RX **and** MCU responses (kernel routes them here via
`RXEVT_EP4_EN`).

**Firmware load must be strictly lockstep.** Send one MCU command, wait for its seq-matched ack
on EP `0x84`, then proceed; FW_SCATTER chunks go on EP `0x04` between commands. If commands
outrun the chip it acks the patch session, goes silent through the whole RAM phase, and FW_START
hits an uninitialized chip and wedges (EP0 dies). The same wait fixes the SuperSpeed first-chunk
short-write — the chip needs the post-PATCH_START setup window before it can sink bulk data. The
boot signal is the `MCU_EVENT_FW_START` (eid 0x01) response to FW_START; `FW_N9_RDY` over EP0 is
only a best-effort secondary confirmation (EP0 can briefly lag after the handoff).

**Post the RX IN-URB drainer before `dma_init`** (kernel order: `mt76u_alloc_queues` precedes
`mt792xu_dma_init`) — `GLO_CFG`'s `RX_DMA_EN` backs up if no RX URBs are queued.

**No userland cold reset on Windows.** Once firmware runs, `dev.reset()` re-acquires at the same
bus address still running; a physical replug is the only way to force a fresh cold boot. The
single-function PAU0F drops to cold on its own when idle, so it is rarely warm between runs.

**Do NOT cold-boot a warm chip — that poisons it on WinUSB.** A warm chip (firmware still running
from a prior run) is reattached, not rebooted (kernel `mt7921u_resume` model): light
`dma_init(resume=True)` gated on the `MT_WFDMA_NEED_REINIT` latch, re-post RX, re-sync channel —
no `wfsys_reset`, `mcu_power_on`, firmware reload, or post-boot init. Firing the cold-boot ops
(`wfsys_reset` / `mcu_power_on`) at a still-running chip is what causes the `Errno 32` bulk-pipe
stall — *not* reading the warm bit (reading `MT_CONN_ON_MISC` leaves RX streaming untouched). The
kernel's PROBE path can `usb_reset_device` before its warm reset, but libusbK's `dev.reset()` is a
no-op on this single-node composite device, so we can't replicate PROBE on WinUSB — and don't need
to, since RESUME needs none of it. `set_hif_suspend(false)` is intentionally omitted: a
cross-process reconnect never suspended the HIF, so there is nothing to un-suspend.

## Board variants (any-card support)

mt7921/MT7961 is firmware-driven, so per-card EFUSE cal (TX power, PA, temp) is applied
inside the MCU and never surfaces host-side — the host sends only the world-domain
regulatory SKU (`txpower.py`, deterministic). The only genuinely per-card VALUE is the MAC,
which was already read at runtime (`parse_nic_capability`, MT_NIC_CAP_MAC_ADDR). The host-side
branches that key on the runtime `GET_NIC_CAPAB` reply are now derived from it (a 1:1 mirror of
the kernel), not hardcoded, so the driver runs on any card's caps and defaults to the captured
reference (`verify_pcap` byte-unchanged on both pau0f + AXML):

- **`mcu.NicCaps`** (`parse_nic_capability`) parses the PHY cap TLV → `antenna_mask = BIT(nss)-1`
  and `has_2ghz`/`has_5ghz` (hw_path bits), plus `has_6ghz` (MT_NIC_CAP_6G). [SRC mt7921/mcu.c:525-554,596-601]
- **`txpower.rate_txpower_payloads(caps)`** gates the 2.4/5/6 GHz batches on `has_*ghz` and picks
  `last_ch` from the highest present band. [SRC mt76_connac_mcu.c:2183-2188,2260-2284]
- **`mcu.set_chan_info(..., antenna_mask)`** SET_RX_PATH tx/rx streams, and **`rx.decode_frame(data,
  antenna_mask)`** RSSI loop, thread the runtime `antenna_mask`. [SRC mt7921/mac.c:365-378]

`connect()` logs the detected caps once (`driver._log_nic_caps`), tagged `[untested variant]` when
they differ from the reference (antenna_mask 0x3, 2.4+5+6 GHz).

**Residual / caveat.** For `0e8d:7961` the caps are FIXED silicon — both captured units are
identical (nss=2, hw_path=0xF, has_6ghz=1), and no `0e8d:7961` variant with different caps is
known. So the non-reference branches (1x1 antenna_mask, band-gated txpower, single-chain RSSI) are
ported-from-C but **hardware-untested** — there is no cold-boot capture to gate them; they run
give-it-a-shot. `NicCaps()`'s bare default is `has_6ghz=False` (kernel-faithful for a missing 6G
TLV), so a malformed reply drops the 6 GHz sweep; the captured reference reply carries the 6G TLV
(=1) and reproduces the full 3-band wire. Coverage: `tests/chips/mt7921au/test_chip_variant.py`.

## Orientation

Boot lives in the firmware-load path: MCU power-on (`MT_VEND_POWER_ON`, poll `MT_CONN_ON_MISC`
BIT0) → post RX drainer → `dma_init` (WFDMA register init) → `MT_SWDEF_MODE`/`MT_UDMA_TX_QSEL` →
lockstep firmware load. Post-boot device init (NIC capability, EFUSE buffer mode, `mac_init`,
regdomain, TX-power SKU, MAC enable, RX path, DEV/BSS info) is `init.py` / `mac.py` / `mcu.py` /
`txpower.py` / `regdomain.py`. Monitor entry + channel tune is `config_sniffer` (`mcu.py`,
`ch_band` 1/2). RX decode is `rx.py` (connac2 packet-type demux + `mt7921_mac_fill_rx`,
RCPI→RSSI). TX is `tx.build_tx` → `mt76_connac2_mac_write_txwi`; mgmt/ctrl take the PSD/LMAC path
(fixed lowest rate, EP 0x09), data take their AC (EP 0x04). Warm reattach is
`driver._warm_reattach`. Exact register values are `constants.py` — treat that as source of
truth, this doc for structure. Names match the kernel C in `data_dumps/mt76-source-v6.18/`.

Wire structure worth knowing: MCU command on EP `0x08` is `[4B SDIO hdr][64B
mt76_connac2_mcu_txd][payload][pad]`, the SDIO hdr being `tx_bytes = 64 + payload_len`; the
device echoes the command's `seq` in its response, which is how responses are matched. FW_SCATTER
short-circuits the txd to `[4B SDIO hdr][chunk][pad]`, 4096 B/chunk. The `_1_` firmware variant
(`WIFI_MT7961_patch_mcu_1_2_hdr.bin` + `WIFI_RAM_CODE_MT7961_1.bin`, sha256-verified vs Kali
6.18.12 linux-firmware) is always used for `0e8d:7961`.

## Scripts

- `verify_pcap.py` — the offline cold-boot byte gate (4 checks: dma_init, FW handshake, full post-boot stream, TX descriptors); refuses non-`*-scatter` captures since they lack RX.
- `probe_pau0f.py` — confirms negotiated USB speed (USB-3→USB-2 adapters often still go SuperSpeed).
- `warm_c_attach.py` — reattaches a warm chip, streams RX, drives `set_channel` with no boot (evidence the light path works).
- `analyze_usb_traffic.py` — per-endpoint RX/TX tally.
- `decode_fw_handoff.py` — FW_START timeline + per-command response decode.

## Debug log

### 2026-06-27 — first Linux bring-up: device setup needs a replug gate

Device setup (udev rule + modprobe blocklist) install followed by auto-connect failed on Linux:
the rules apply only on the next device-add, so the kernel `mt7921u` still owned the interface and
every `claim_interface` / control transfer came back `[Errno 13] Access denied` — `connect()` never
reached the silicon (the warm-check read EACCES'd and defaulted to cold, then chip-id EACCES'd →
fail). Not a bring-up bug; the driver was locked out. Fix: `LINUX_REPLUG_AFTER_MODPROBE = True`
(mirrors mt76x0u), so the flow installs the rules then prompts for a replug instead of
auto-connecting. After the replug the card re-enumerates cold (kernel blocklisted, udev rule live)
and the cold boot runs clean. Post-replug `test_hw_mt7921au` is a full PASS on Linux: cold firmware
boot, post-boot init, 2.4 GHz RX (~350 frames/3 s CH1), 5 GHz RX (CH36/44/149/157, ~1100 total).

### 2026-06-12 — warm reattach, the reset dead end, and the break-it bugs

A long detour tried to cold-boot a warm chip (`wfsys_reset` + re-acquire + `load_firmware`) and
kept hitting `Errno 32` bulk-pipe stalls. Bisected with zero driver code to a clean-warm chip:
the stall is the cold-boot ops fired at a running chip, not the warm-bit read. The one "426-frame"
success was a non-reproducible fluke. Light reattach (RESUME model) then worked: cold → close →
warm reattach in ~5 ms, 400-500 frames/3 s, repeatable back-to-back with no replug.

Break-it (human) HW-validation surfaced two bugs, now fixed: (a) RX delivered the whole USB buffer
instead of `data[mpdu_off:MT_RXD0_LENGTH]`, so trailing alignment padding let the beacon IE walk
over-read (a stray RSN left a WEP AP stuck as WPA2) and corrupted WEP-ICV / WPS-HMAC / frag length
math; (b) injected frames reused seq 0 (the chip transmits the TXD SN_VALID seq, no auto-assign)
so APs deduped interactive attacks — `inject_frame` now stamps an incrementing frag-preserving
`seq_ctrl` via `tx.stamp_seq_ctrl`.

### 2026-06-21/22 — 5 GHz inject investigation

5 GHz inject was suspected to fail in `tx._tx_rate_val`'s `band_5ghz` branch. Audited it
leaf-for-leaf against `mt76_connac2_mac_tx_rate_val` and ruled it out — the band flag reaches, the
rate value is the correct HW PLCP OFDM 6 Mbps, and the FIXED_RATE TXD block is 1:1 with the kernel
(promoted to Gotchas). 5 GHz unicast-data inject had been CCK-rated because FIX_RATE dropped the
USE_MINRATE condition — fixed in `8798c38d`. 5 GHz RX + inject were HW-confirmed 2026-06-22, but
the WPS/PMKID-on-5 GHz failure points outside the TXD, leading suspect 5 GHz TX power / per-channel
cal. Next: capture a 5 GHz aireplay session (`capture.py --bssid5g/--channel5g/--client5g`) and
byte-diff the driver's 5 GHz inject — this analysis predicts a MATCH, which would confirm the TXD
and point at RF/TX-power, then check whether the sniffer channel-switch needs an explicit 5 GHz
TX-power program (the connac `SET_RATE_TX_POWER` path the monitor port omits).
