# MT7921AU Protocol Notes

This file accumulates **verified** ground-truth facts about the MT7921AU bring-up sequence. Every claim here must be confirmed against `usb_dumps/captures_mt7921u/capture-3.pcap` (the cold-boot Linux trace, bus 4, device 19, vid:pid `0e8d:7961`).

If something isn't in this file, it has NOT been verified — treat anything in `constants.py`, `firmware.py`, etc. as a hypothesis until confirmed here.

## USB Topology (Interface 3 of MT7921AU)

The MT7921AU exposes a Wireless-class composite device. Interfaces 0/1/2 are standard wireless-class endpoints. **Interface 3 is `Vendor Specific` and is the one the mt76 driver actually uses.**

Endpoints on Interface 3 (from descriptor in capture-3, frames 51–100):

| Address | Direction | Max Packet | Purpose (Linux logical name) |
|---------|-----------|------------|------------------------------|
| `0x84`  | IN  bulk  | 1024       | `MT_EP_IN_PKT_RX` (RX 802.11 packets) |
| `0x85`  | IN  bulk  | 1024       | `MT_EP_IN_CMD_RESP` (MCU command responses) |
| `0x08`  | OUT bulk  | 1024       | `MT_EP_OUT_INBAND_CMD` (MCU commands) |
| `0x04`  | OUT bulk  | 1024       | `MT_EP_OUT_AC_BE` (FW_SCATTER + 802.11 TX data) |
| `0x05`  | OUT bulk  | 1024       | `MT_EP_OUT_AC_BK` |
| `0x06`  | OUT bulk  | 1024       | `MT_EP_OUT_AC_VI` |
| `0x07`  | OUT bulk  | 1024       | `MT_EP_OUT_AC_VO` |
| `0x09`  | OUT bulk  | 1024       | `MT_EP_OUT_HCCA` |
| `0x86`  | IN  bulk  | 2          | unused (event?) |

Linux's `mt76u_set_endpoints` iterates Interface 3's endpoints in descriptor order and assigns logical names in the order `MT_EP_OUT_INBAND_CMD, MT_EP_OUT_AC_BE, MT_EP_OUT_AC_BK, MT_EP_OUT_AC_VI, MT_EP_OUT_AC_VO, MT_EP_OUT_HCCA`. That maps to physical EPs **0x08, 0x04, 0x05, 0x06, 0x07, 0x09**.

**Current `constants.py` has `EP_OUT_FW = 0x08` and `EP_OUT_DATA = 0x09` — both wrong. Correct:**
- `EP_OUT_MCU = 0x08`
- `EP_OUT_FW  = 0x04` (firmware chunks and 802.11 data)

## First Bulk OUT Activity (frames 14182+)

Captured frames after a cold plug-in. Decoded from `usb.capdata`. All multi-byte fields are little-endian.

### Frame layout for an MCU command (non-FW_SCATTER) on EP 0x08

```
[ 4 bytes  ] SDIO header:  tx_bytes(15:0) | pkt_type(17:16)=0
[ 64 bytes ] mt76_connac2_mcu_txd
[ payload  ] command-specific bytes
[ pad      ] to round up total to 4-byte aligned + 4 trailing bytes
```

The 64-byte `mt76_connac2_mcu_txd` is:

```
offset 0  (32 bytes): __le32 txd[8]   -- hardware descriptor
offset 32 (2 bytes):  __le16 len      -- skb->len minus sizeof(txd[8])
offset 34 (2 bytes):  __le16 pq_id    -- 0x8000 = MCU_PQ_ID(MT_TX_PORT_IDX_MCU=1, MT_TX_MCU_PORT_RX_Q0=0x20)
offset 36 (1 byte):   u8 cid          -- command id (e.g. 0x10 = PATCH_SEM_CONTROL)
offset 37 (1 byte):   u8 pkt_type     -- MCU_PKT_ID = 0xA0
offset 38 (1 byte):   u8 set_query    -- MCU_Q_NA=3 for plain commands
offset 39 (1 byte):   u8 seq          -- starts at 1, wraps in low nibble
offset 40 (1 byte):   u8 uc_d2b0_rev  -- 0
offset 41 (1 byte):   u8 ext_cid      -- 0 unless using MCU_EXT_CMD
offset 42 (1 byte):   u8 s2d_index    -- MCU_S2D_H2N = 0
offset 43 (1 byte):   u8 ext_cid_ack  -- 0
offset 44 (20 bytes): u32 rsv[5]      -- 0
```

`txd[0]` and `txd[1]` are populated by `mt76_connac2_mcu_fill_message`:
- `txd[0]` = `MT_TXD0_TX_BYTES(skb->len) | MT_TXD0_PKT_FMT(MT_TX_TYPE_CMD=2) | MT_TXD0_Q_IDX(MT_TX_MCU_PORT_RX_Q0=0x20)`
  → with payload 4: `0x41000044`
- `txd[1]` = `MT_TXD1_LONG_FORMAT | MT_TXD1_HDR_FORMAT(MT_HDR_FORMAT_CMD=1)` = `0x80010000`
- `txd[2..7]` = 0

### Frame 14182: first MCU command sent by Linux

Capdata (76 bytes):
```
44 00 00 00 44 00 00 41 00 00 01 80 00 00 00 00
00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00
00 00 00 00 24 00 00 80 10 a0 03 01 00 00 00 00
00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00
00 00 00 00 01 00 00 00 00 00 00 00
```

Decoded:
- SDIO hdr `0x44` = 68 (txd_len 64 + payload 4)
- `mcu_txd.len` = 0x0024 = 36 = (txd_len_minus_hw_descriptor 32 + payload 4)
- `mcu_txd.pq_id` = 0x8000
- **`mcu_txd.cid` = 0x10 → MCU_CMD_PATCH_SEM_CONTROL**
- `mcu_txd.pkt_type` = 0xA0 (MCU_PKT_ID)
- `mcu_txd.set_query` = 0x03 (MCU_Q_NA — no ext_cid, no CE flag)
- `mcu_txd.seq` = 0x01 (first message)
- Payload (4 bytes): `01 00 00 00` — request semaphore (`PATCH_SEM_GET = 1`)

### Frame 14186: second MCU command (84 bytes, payload 12)

cid = 0x05 = MCU_CMD_PATCH_START_REQ. Payload contains the patch download address/size info.

### Frame 14236: cid=0x07 PATCH_FINISH_REQ
### Frame 14240: cid=0x10 PATCH_SEM_CONTROL (release semaphore)
### Frame 14435+: cid=0x01 TARGET_ADDRESS_LEN_REQ (per RAM section)

### Firmware data chunks on EP 0x04 (frames 14190–14234, etc.)

Each chunk is 4104 bytes:
```
[ 4 bytes ] SDIO header: tx_bytes = 0x1000 = 4096, pkt_type = 0
[ 4096 bytes ] raw firmware payload
[ 4 bytes ] trailing zero padding
```

Linux `__mt76_mcu_send_firmware` paces these out with `cmd = MCU_CMD(FW_SCATTER)`. In `mt76_connac2_mcu_fill_message`, FW_SCATTER short-circuits BEFORE adding the 64-byte mcu_txd — only the 4-byte SDIO header is prepended.

## Findings vs current Python code

The Python implementation in `src/wifit3/chips/mt7921au/` was scaffolded without first decoding the capture. Known incorrect items (do not trust without re-verification):

1. **Endpoints**: `EP_OUT_FW`, `EP_OUT_DATA` numerically wrong (see table above).
2. **`firmware._build_mcu_header`**: builds a 16-byte mash-up that doesn't correspond to either the SDIO header or the connac2 MCU TXD.
3. **`firmware.load_firmware`**: skips the patch-session wrapping (`PATCH_SEM_CONTROL`/`PATCH_START_REQ`/`PATCH_FINISH_REQ`) and the `TARGET_ADDRESS_LEN_REQ` calls needed for the RAM blob.
4. **`firmware.load_firmware` strips first 192/128 bytes of the firmware files** — unverified; Linux uses the full file via `mt76_connac2_fw_trailer` header parsing.

### `DL_MODE` bit position — corrected 2026-05-17

Earlier this doc and `constants.py` claimed the wire `mode` field for plain RAM/patch sections was `0x00800000` (BIT 23), arguing the kernel source's `DL_MODE_NEED_RSP = BIT(31)` was "wrong" because the pcap looked different. That was a **hex-offset miscount** — I lined hex chunks up by eye and ended up 4 bytes short, reading the trailing-pad zeros of `mcu_txd` as if they were the `mode` field. Re-parsed programmatically against capture-3 frame 14186:

```
SDIO hdr (4B) + mcu_txd (64B) + payload (12B struct + 4B pad)
bytes 68-71 = 00 00 90 00  →  addr = 0x00900000   (matches patch base)
bytes 72-75 = 80 67 01 00  →  len  = 0x00016780   (matches patch size 91520)
bytes 76-79 = 00 00 00 80  →  mode = 0x80000000   (= BIT 31, matches source DL_MODE_NEED_RSP)
```

Wire bytes match Linux source. The previous incorrect value was sent on five firmware-load commands (PATCH_START_REQ + 4 × TARGET_ADDRESS_LEN_REQ), causing the boot ROM to accept bytes but never finalize the download — observed symptom was FW_START_REQ jumping into an uninitialized PC and EP0 going dead. Fixed in `constants.py`.

## MCU response behavior on EP 0x85

**Verified 2026-05-17 (with `DL_MODE_NEED_RSP = BIT(31)` correct):**

With the bit set, the device sends a 36-byte `mt76_connac2_mcu_rxd` response on EP 0x85 for every firmware-load command:
- `PATCH_SEM_CONTROL` (GET → `0x02 PATCH_NOT_DL_SEM_SUCCESS`, RELEASE → `0x03 PATCH_REL_SEM_SUCCESS`)
- `PATCH_START_REQ`, `PATCH_FINISH_REQ`
- `TARGET_ADDRESS_LEN_REQ` (one per region)

`FW_START_REQ` does NOT produce a response on EP 0x85 (verified by 0 entries in `_mcu_rx_queue` after sending it). Linux's pcap confirms — no IN data on EP 0x85 anywhere, and zero data captured on EP 0x84 either, until 18ms after FW_START_REQ when a **0-length URB completes successfully on EP `0x84`** as the firmware-boot signal (capture-3 frame 14799 / capture-1 frame 14969).

**MCU command CID routing depends on `MT_WFDMA_HOST_CONFIG_USB_RXEVT_EP4_EN`** (BIT 6 of `0x7c027030`):
- Cleared: MCU responses route to EP 0x85. ← our setup
- Set: MCU responses route to EP 0x84 (verified empirically — PATCH_SEM response moved there when we set the bit).

Linux sets this bit (`mt792xu_dma_rx_evt_ep4`) but appears to tolerate the response-routing change because its `wait=true` calls silently time out (kernel pcap captures zero data on either EP 0x84 or 0x85 IN throughout firmware load). We keep the bit cleared because our code uses the PATCH_SEM_CONTROL response to drive state.

**Current decision:** wait for response on PATCH_SEM_CONTROL; treat data-flow commands as fire-and-forget. The drainer queues other responses silently. Firmware-up signal is `FW_N9_RDY` poll succeeding (which depends on the device's EP0 staying alive — currently the blocker on WinUSB).

## USB 2.0 vs USB 3.0 on Windows (CRITICAL)

**On USB 2.0 (HighSpeed): firmware upload works.** Verified by user with a real USB 2.0 hub/extender. Patch session completes, RAM region 0/1/2 upload, FW_START_REQ goes out.

**On USB 3.0 (SuperSpeed) via WinUSB: bulk OUT to EP 0x04 stalls at exactly 4 USB packets.** Pattern verified across chunk sizes 1016B, 1024B, 4096B — always exactly 4 packets accepted, then 5+ NAK indefinitely. Both `set_configuration()` removal and `clear_halt()` after claim did NOT fix it. Likely a USB 3.0 NRDY/ERDY flow-control interaction between WinUSB and the boot ROM. Needs dedicated investigation later — for now: **test on USB 2.0 ports/hubs on Windows**, USB 3.0 should work on Linux (per Linux's pcap showing 22+ chunks fly through with no stall).

⚠ Don't be fooled by passive "USB 3 to USB 2" adapters — many of them still let the device negotiate SuperSpeed. Use `python scratch/check_usb_speed.py` to verify `speed: 3 (HIGH)`.

## FW_SCATTER 4-packet stall (Windows / WinUSB / USB 3.0)

The MT7921AU boot ROM accepts exactly **4 USB packets** of FW_SCATTER bulk data, then NAKs subsequent OUTs until the bulk transfer times out. Pattern verified across three chunk sizes:

| chunk_size | wire bytes/chunk | packets/chunk | chunks accepted | total packets |
|-----------:|-----------------:|--------------:|----------------:|--------------:|
| 4096       | 4104             | 4 full + 1 short = 5 (transfer short-writes after 4) | 0 (PyUSB returns 4096/4104) | 4 |
| 1024       | 1032             | 1 full + 1 short = 2 | 2 | 4 |
| 1016       | 1024             | 1 full = 1 | 4 | 4 |

Always 4 packets. `bMaxBurst = 0` in all USB 3.0 SS Endpoint Companion descriptors, so it's not a USB burst-size issue. Most likely: USB 3.0 `NRDY`/`ERDY` flow control between WinUSB and the boot ROM stack doesn't handshake correctly, so after the first batch fills the device's tiny FIFO, the host can't resume.

Linux's pcap (capture-3) shows ~22 4104-byte chunks flowing back-to-back with no stalls, so Linux's USB stack handles this fine. The issue is WinUSB-specific.

**Workarounds to investigate:**
1. Force USB 2.0 (plug into USB 2.0 port or hub) — bypasses USB 3.0 flow control entirely. Most promising.
2. Inter-chunk pacing — added 10ms `asyncio.sleep` between chunks; may unblock if it's a timing issue.
3. Use libusb async URB API (queue multiple URBs) instead of synchronous `Device.write()` — closer to what the Linux kernel does.

### Firmware variant selection (clarified)

There are two firmware-name pairs in `data_dumps/mt76-source-v6.18/mt792x.h:44-53`:

| SKU | Patch | RAM |
|-----|-------|-----|
| MT7921 (chip_id 0x7961) | `WIFI_MT7961_patch_mcu_1_2_hdr.bin` | `WIFI_RAM_CODE_MT7961_1.bin` |
| MT7920 (promoted from 0x7961 if `MT_HW_BOUND & BIT(7)`) | `WIFI_MT7961_patch_mcu_1a_2_hdr.bin` | `WIFI_RAM_CODE_MT7961_1a.bin` |

The "promote 0x7961 → 0x7920" check lives **only in the PCI driver** (`mt7921/pci.c:357-360`). The USB driver (`mt7921/usb.c:15-30`) unconditionally pins every supported VID:PID to `MT7921_FIRMWARE_WM`, and `modinfo mt7921u.ko` declares only the `_1_` files as firmware deps (`kalitrip/modinfo.txt:6-7`). **Our card (USB `0e8d:7961`) is therefore always the `_1_` variant.** The trailing `a` in `Build Time: 20250625153620a` is just part of the embedded build-stamp inside the patch header — not a variant marker.

## Session pause snapshot (2026-05-17)

Bring-up was paused after extensive iteration in this state:

**Verified correct (don't re-investigate without new evidence):**
- All 6 host-to-device firmware-load MCU commands are **byte-for-byte identical** to pcap (programmatic diff against capture-3 frames 14182/14186/14236/14240/14435/14797). See `_build_mcu_frame` in `transport.py`.
- Endpoints (Interface 3 vendor-specific): IN bulk 0x84/0x85, OUT bulk 0x08 (MCU)/0x04 (FW data + AC_BE)/0x05/0x06/0x07/0x09, IN interrupt 0x86. Confirmed twice — pcap descriptors + `kalitrip/usb3/lsusb_verbose.txt`.
- Firmware blobs in `assets/`: byte-identical to Kali 6.18.12's `_1_` variant (sha256 verified).
- `DL_MODE_NEED_RSP = 0x80000000` (BIT 31) in `constants.py` — matches wire bytes.
- Firmware-load command sequence: PATCH_SEM_GET → PATCH_START_REQ → FW_SCATTER chunks → PATCH_FINISH_REQ → PATCH_SEM_REL → 4× (TARGET_ADDR_LEN + FW_SCATTER chunks) → FW_START_REQ. Matches captures 1 and 3 (capture-2 is a warm boot — chip already running, kernel skipped load).
- Pre-patch DMA scheduler init (`_dmashdl_init` — 16 GROUP_QUOTA + 4 Q_MAP + 2 SCHED_SET + REFILL/PAGE/PKT_MAX_SIZE rmws). Matches `mt792xu_wfdma_init` lines 153-173.
- MCU responses arrive on EP 0x85 with BIT(31) set — see "MCU response behavior" section above.

**Blocker:** on Windows / WinUSB, after `FW_START_REQ` succeeds the chip's EP0 control endpoint goes dead. No data on EP 0x84 (the firmware-up ZLP Linux sees at +18ms), no FW_N9_RDY bit set, no response to any vendor read for 20+ seconds. Same wire bytes as Linux's pcap up through FW_START_REQ produce different post-boot behavior.

**Hypotheses for next session (not yet tested):**
1. WinUSB on Windows mishandles the USB-stack event the device emits at firmware handoff (ZLP, soft reset, port reconfig). Kernel handles it transparently, WinUSB doesn't surface it.
2. The device requires a larger pool of pre-submitted bulk-IN URBs than our one-at-a-time `dev.read()` synchronous loop maintains. Linux pre-submits 128 per endpoint via `mt76u_alloc_queues`.
3. Some pre-patch init we haven't replicated — but DMASHDL + WLCFG + dma_rx_evt_ep4 cover the known cold-boot register writes. `mt792xu_dma_prefetch` (TX ring extension control, 7 RMWs) is the only remaining unimplemented chunk of `mt792xu_wfdma_init`, likely not boot-critical.

**Recommended first move on resumption:** test the current code on Kali (boot live USB, `rmmod mt7921u`, install Wifit3, run `python scratch/test_hw_mt7921au.py`). If firmware boots on Kali but not on Windows, hypothesis 1 or 2 is confirmed and we focus on Windows USB compat. If it fails on Kali too, we have a genuine code bug we haven't isolated yet — and Kali gives us full `dmesg` / `usbmon` for debugging.

**Known Windows-specific compat issues (don't re-discover):**
- UHW bus (`bmRequestType 0x5E/0xDE`) returns `Errno 5 I/O Error` on every transfer. Not used for cold-boot anymore (bulk-EP reset bits are already clear — `_epctl_release_reset` is a no-op state change).
- USB 3.0 SuperSpeed has the 4-packet FW_SCATTER stall (see section above). USB 2.0 ports/hubs work.

## Kali handoff (2026-05-19) — see [KALI-HANDOFF-2026-05-19.md](./KALI-HANDOFF-2026-05-19.md)

User ran `scratch/test_hw_mt7921au.py` on Kali 2026.1 live USB against the

Most-likely culprit: **kernel `mt7921u` driver was still bound** to the device's
Interface 3 when the test ran. dmesg shows `mt7921u` repeatedly initializing on
this device through the session (vendor-request `-110 ETIMEDOUT` bursts every
~3.2 s), and the device migrated Bus 4 → Bus 2 mid-session. `lsusb -t` showing
`Driver=[none]` on If 3 may have been a stale snapshot or the brief window before
the kernel re-grabbed it.

Companion raw evidence (lsusb, dmesg, usbmon2 capture, test output) is in
`usb_dumps/notes_mt7921au/`.

**Next-resumption recipe** (lifted from the handoff doc):

2. `sudo rmmod mt7921u mt7921_common mt76_connac_lib mt76_usb mt76`
3. Replug, verify `lsusb -t` + `dmesg | tail` show no `mt7921u` lines
