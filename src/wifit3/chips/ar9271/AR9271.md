# AR9271 (`ath9k_htc`) Userspace Driver

## Potential Known Gaps

Cross-driver gap classes (project audit 2026-05-25). **Offline analysis only —
no hardware available; verify before `[x]`.**

- [x] **RX filter / monitor mode (promiscuity)** — FIXED + HW-CONFIRMED
  2026-05-25 (`scripts/ar9271/test_rxfilter_probe.py`). ath9k_htc only sets
  `AR_RX_FILTER` with the **PROM** bit when monitoring [SRC htc_drv_txrx.c:884]
  and re-applies it after every reset/channel-change; the replayed init never
  held it and `set_channel` (tuning replay) never wrote `0x803c`, so PROM was
  never (re)established. Fix: `_apply_monitor_rx_filter` WMI-writes
  `AR_RX_FILTER=0xC03F` after connect AND after each `set_channel`. The probe
  confirms it works: 130-210 **unicast-between-others** frames/7s captured per
  channel (incl. `type=data to_ds=True` between third parties) — genuinely
  promiscuous. [WIRE captures_ath9k_htc frame 3047 = exact kernel write.]
- [x] **RX polling loop drops frames** — N/A for ar9271 (HW-measured, NOT
  ported, correctly). `test_pollgap_load.py`: under a synthetic loop hog
  (~25ms busy every 100ms) RX did NOT drop (933 vs 635 frames/8s). ar9271's two
  independent executor read-tasks (Control + Data EP) keep reads in flight even
  when the loop is starved, unlike the single-loop Realtek pattern. So the
  reader-thread port is unnecessary here — good, since its async HTC dispatch
  made it a risky conversion anyway.

### OPEN (diagnosed offline 2026-05-25 — awaiting HW confirmation)
- **Cold-boot PMKID hangs** (warm works). **FIXED + HW-CONFIRMED 2026-05-25.**
  Root cause: DATA-endpoint credit starvation, not toggle bits (hence
  `reset_pipes()` was no fix). `inject_frame` → `transport.send(EP 5, …)` →
  `credit_manager.acquire(5)` blocks until EP 5 has a credit. The warm path
  seeds it (`set_initial(data_endpoint_id, 33)`, driver.py is_warm branch); the
  cold path never did (HTC READY grants initial credits only to EP 1 + EP 2,
  and the device only *replenishes* an endpoint after the host consumes a
  credit on it — so EP 5 sat at 0 forever cold). RX uses no credits → fine cold.
  Fix: seed `data_endpoint_id` credits at the end of the cold connect, mirroring
  the warm path (driver.py, after `_apply_monitor_rx_filter`). User confirmed
  PMKID extraction works first-try on cold boot.
- **No passive 4-way captured in-app — ROOT-CAUSED + FIXED 2026-05-25: QoS
  alignment padding broke the FCS check.** ath9k inserts `hdrlen & 3` bytes of
  DMA padding *after* the MAC header so the payload is 4-byte aligned (2 bytes
  for a 26-B QoS header), but the over-the-air FCS excludes it. `parse_rx_frame`
  ran CRC32 over the *padded* frame → every QoS frame failed the FCS gate.
  Since beacons/non-QoS use a 24-B header (`pad=0`) they passed — which is why
  scanning worked but **all downlink-unicast data AND the entire 4-way (M1-M4
  are QoS) were silently dropped**. Fix: `_strip_alignment_padding` removes the
  pad before the FCS check + parse, mirroring kernel `ath9k_rx_skb_postprocess`.
  **HW-confirmed 2026-05-25: full M1-M4 captured, warm and cold.** 9 captured
  EAPOL frames all FCS-validate only after the strip and decode as eapol;
  regression test in `tests/chips/ar9271/protocol/test_wmi.py`. A lean
  DEBUG-gated `[RXGATE]` tally in `wmi.parse_rx_frame` (direction × gate-outcome,
  EAPOL highlight) is kept as the ar9271 RX debug aid that found this; not yet
  generalised across drivers (see project gap-audit). *Earlier refuted
  hypotheses, kept so they aren't re-chased:*
  - *Parse mis-alignment* (EAPOL decoded as data): refuted. A temporary
    `[EAPOL-MISPARSE?]` probe (scanned "data" frames for the 0x888E LLC/SNAP
    sig) stayed **silent** across a locked-channel phone-reconnect run — no
    EAPOL surfaced as mis-parsed data (it was failing FCS upstream). Probe
    since removed.
  - *RX-filter / BSSID-mask config*: refuted against the **airmon-ng pcap ground
    truth** (`usb_dumps/captures_ath9k_htc/capture-1.pcap`, `airmon-ng start`
    window = frames 1543–6406, decoded via WMI REG_WRITE 0x0015). The mainline
    kernel monitor recipe is: `AR_STA_ID0/1`=device MAC; **`AR_BSSMSKL/U` =
    `0xFFFFFFFF`/`0x0000FFFF` (all-ones EXACT-match mask)**; `AR_BSS_ID0/1`=0;
    `AR_RX_FILTER`=`0xC03F` (PROM) re-issued per channel-set (+ companion
    `0x810c`=0). It relies entirely on the **PROM bit** for promiscuity — NOT a
    zero mask. We already write the identical `0xC03F`, so there is no missing
    RX-filter register. (frame 3047 == our `_apply_monitor_rx_filter`.)
  The hard datum: in a 21 s capture **locked on NETGEAR2G's channel**, we received
  **192 uplink** unicast frames (`to_ds`, RA=BSSID) and **0 downlink-unicast**
  (`from_ds`, RA=an individual client) — where the 4-way's M1/M3 live. PROM is
  thus only *partially* effective on the cleanroom FW (passes RA=other-BSSID but
  not RA=other-client). **Instrumentation added** (`wmi.parse_rx_frame`,
  DEBUG-gated `[RXGATE]`): classifies every post-magic frame by direction +
  addr1 type and logs which acceptance gate (rs_status / declared_len / fcs) it
  cleared or died at, plus samples magic-fail payloads (`ar9271_rx_magicfail.log`)
  in case downlink unicast wears a different RX descriptor. Decisive test = focus
  on NETGEAR2G (locked), `WIFIT3_LOG=debug`, reconnect a phone, then read `[RXGATE]`:
  DL-UNICAST seen but dropped at a gate → our RX-path bug (fixable); DL-UNICAST
  never seen (and magic-fail samples aren't 802.11 data) → cleanroom FW/PHY never
  hands it up. Don't re-chase RX-filter/poll/parse — all settled.

Userspace Python driver for the Atheros AR9271 (e.g. ALFA AWUS036NHA) over
PyUSB. Targets monitor mode + injection + handshake/PMKID capture without
the OS wireless stack (NDIS/mac80211).

## Hardware

- **Chip:** Atheros AR9271 (soft-MAC, 1T1R, 2.4 GHz only)
- **VID/PID:** `0x0CF3:0x9271`
- **Firmware:** `htc_9271_cleanroom.fw` (shipped in `assets/`). Diverges from
  mainline `htc_9271.fw` in event IDs, RX header layout, and HIF tags — see
  the Protocol section below for the verified differences.
- **Platforms:** Windows (WinUSB via Zadig) and Linux (libusb after
  `rmmod ath9k_htc`).

## Protocol (verified, cleanroom firmware)

The cleanroom firmware does NOT match the mainline `ath_htc_rx_status`
struct. The values below were decoded from real hw captures (see
`WIFIT3_AR9271_DUMP_RX` diagnostic in `protocol/wmi.py`) and validated
against the kernel ground truth at `data_dumps/ath9k-source-v6.18/`.

### USB endpoints

| EP | Direction | Role |
|---|---|---|
| `0x01` | Bulk OUT | Injected 802.11 frames (data path) |
| `0x04` | Bulk OUT | WMI commands, HTC management |
| `0x82` | Bulk IN | RX frames + WMI events (HIF stream) |
| `0x83` | Interrupt IN | HTC control (e.g. `READY` event 0x0001) |

### HIF wrapper (Bulk-IN stream)

Every chunk on EP `0x82` is wrapped:

```
[pkt_len: LE16][pkt_tag: LE16][HTC frame: pkt_len B][zero-pad to 4 B]
```

- `pkt_tag` is `0x4e00` (`ATH_USB_RX_STREAM_MODE_TAG`); TX uses `0x697e`.
- Chunks bundle freely within one USB transfer **and** span transfers —
  our `transport.AR9271USBTransport._handle_bulk_in` mirrors the kernel's
  `ath9k_hif_usb_rx_stream` (`hif_usb.c:553`) including the partial-frame
  carry-over buffer and the flush-on-tag-mismatch resync.
- Interrupt-IN (`0x83`) has **no** HIF wrapper — one HTC frame per URB.

### Cleanroom RX header (36 B before the 802.11 frame)

| Offset | Field | Notes |
|---|---|---|
| 0-3 | `u32` frame counter | Monotonic-ish per RX |
| 4-5 | `be16` frame length | `== len(payload) - 36`, drop on mismatch |
| **6** | `u8` rs_status | **0 = clean, non-zero = FW-flagged RX error** |
| 7 | `u8` zero | |
| **8** | `i8` RSSI chain-0 | SNR above noise floor; `dBm = -95 + rs_rssi` |
| 9 | `i8` RSSI chain-1 | Duplicate of byte 8 on 1T1R |
| **10-15** | 6 B magic | `80 16 80 80 01 FF` — required for sync validation |
| 16 | `u8` rate index | `0x09` short / `0x1b` OFDM, observed |
| 17-23 | zeros | |
| 24 | `i8` RSSI dup | |
| 25 | `u8` | Always `0x01` |
| 26-35 | chain/rate padding | `0x80` filler = "chain unused" |
| 36... | 802.11 frame | FCS in last 4 B, LE-encoded CRC32 |

### Frame-acceptance gate (in `parse_rx_frame`)

In this order — each filter is cheaper than the next, so we shortcut early:

1. **Length sanity:** `len(payload) >= 36 + 14` (smallest ACK).
2. **Magic match:** `payload[10:16] == 80 16 80 80 01 FF`.
3. **rs_status clean:** `payload[6] == 0`.
   The cleanroom firmware doesn't drop RXERR frames the way mainline
   `ath9k_htc` does via `rs_status & ATH9K_RXERR_*` — we do it here.
   100 % of byte6=0x01 frames fail FCS in measurement.
4. **Declared length:** `be16(payload[4:6]) == len(payload) - 36`.
5. **Strip MAC-header alignment padding** (`_strip_alignment_padding`): the
   hardware inserts `ieee80211_hdrlen(fc) & 3` bytes after the MAC header so the
   payload is 4-byte aligned (2 B for a 26-B QoS header, 0 for 24-B mgmt/non-QoS)
   — but the FCS excludes it. MUST happen before the FCS check below, else every
   QoS frame (downlink-unicast data + all 4-way EAPOL) FCS-fails. Mirrors
   `ath9k_rx_skb_postprocess`.
6. **FCS:** `zlib.crc32(frame[:-4]) & 0xFFFFFFFF == le32(frame[-4:])` on the
   de-padded frame. Catches the residual real-RF-noise frames the firmware
   didn't flag.

Typical hw rates in a dense apartment:
- ~20 % drop at rs_status (FW-flagged corruption)
- ~10 % drop at FCS (real RF noise)
- ~70 % net keep rate, every kept frame byte-clean.

### Event ID quirks (cleanroom v1.4)

| Event | Mainline | Cleanroom (this FW) |
|---|---|---|
| Target Ready (Interrupt EP `0x83`) | `0x1001` | `0x0001` |
| Target Ready (Bulk EP `0x82`) | `0x1001` | `0x1001` |
| RX PDU (data) | `0x1002` | `0x0400` |
| RX PDU (beacon) | `0x1002` | `0x0000` |

The driver subscribes to HTC endpoints 0, 1, and 3 on the bulk pipe and
routes all three through `_on_wmi_packet`; the event-ID switch inside
selects which subset goes to `parse_rx_frame`.

## TX path

- Injection frames go to bulk EP `0x01` (NOT EP `0x04` which is for WMI cmds).
- Each is wrapped in a 4-B HIF header `[len LE16][tag=0x697e LE16]` then the
  8-B HTC header, then an 8-B `tx_mgmt_hdr` (node/vif/tid/flags/key_type/
  keyix/cookie/pad), then the raw 802.11 bytes.
- See `AthMetadataLayer.pack_tx_mgmt` for the descriptor layout.

## Channel tuning

There is no high-level "set channel" WMI command. `set_channel` replays a
register-write blast (mostly static PHY warm-up tables, identical across
channels); the actual frequency lock is a single Fractional-N synthesizer word
written to `AR_PHY_SYNTH_CONTROL` (`0x9874`) via `WMI_REG_WRITE` (`0x0015`).

- `constants.py:71` — `AR_PHY_SYNTH_CONTROL = 0x9874`.
- `sequences/tuning.py:4` — `SYNTH_WORDS`: ch1 `0x30a0cccc`, ch6 `0x30a27777`.

The monitor `AR_RX_FILTER` (PROM bit) must be re-applied after every
`set_channel` — see the RX-filter gap note above.

## Architectural notes

- **Single bulk-IN reader.** Parallel `dev.read()` on EP `0x82` produces
  out-of-order URB delivery in PyUSB's sync model — earlier attempts at 4
  concurrent readers caused 40 % FCS-corrupt frames. Real multi-URB pressure
  would need a libusb1 async port (`libusb_submit_transfer` with one
  consumer processing completions in order). Deferred — see NEXT-STEPS.
- **Stop-and-wait WMI.** Commands are synchronous via a 1-slot mailbox; we
  resend on timeout to recover from desynced USB toggle bits.
- **Calibration is offloaded** to a background thread because the 1,094
  WMI commands take ~1 s and would otherwise freeze the UI loop.
