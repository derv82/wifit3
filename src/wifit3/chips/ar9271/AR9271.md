# AR9271 (`ath9k_htc`)

Userspace port of the Atheros AR9271 (soft-MAC, 1T1R, 2.4 GHz only; e.g. ALFA AWUS036NHA) over
PyUSB — monitor + injection + handshake/PMKID without mac80211. VID/PID `0x0CF3:0x9271`. Runs the
shipped `htc_9271_cleanroom.fw`, which diverges from mainline `htc_9271.fw` in event IDs, RX header
layout, and HIF tags — so the protocol was decoded from real hw captures, not the kernel struct.

## Status

Production-ready core, all RX paths hw-verified. Cold + warm boot, firmware upload, full HTC
handshake. Live monitor scan with realistic RSSI; EAPOL M1-M4 + PMKID capture verified against real
APs, cold and warm. TX inject (deauth, mgmt) via bulk-OUT. 30-min 13-channel hop soak passed
2026-06-05 with no degradation.

Suspect: channel-tune accuracy. `set_channel` now writes the correct Fractional-N synth word per
channel (it once shipped a 2-channel placeholder that silently pinned everything else to CH6), but
ath9k's per-channel analog/NF/IQ calibration writes are still not ported. RX works; per-channel
sensitivity is unverified.

## Gotchas

**The cleanroom firmware is its own protocol.** Event IDs, the 36-byte RX header, and the HIF
stream tags don't match mainline `ath9k_htc`. Target-Ready is `0x0001` on the interrupt EP but
`0x1001` on bulk; RX PDUs are `0x0400` (data) / `0x0000` (beacon), not `0x1002`. The header layout
lives in `protocol/wmi.py`; dump raw payloads with `WIFIT3_AR9271_DUMP_RX=N`.

**The cleanroom FW doesn't drop RXERR frames** the way mainline does via `rs_status`, so the
acceptance gate does it in `parse_rx_frame`: every frame with `rs_status` (byte 6) non-zero fails
FCS in measurement and is dropped here.

**DMA alignment padding breaks the FCS unless stripped first.** The hardware inserts
`ieee80211_hdrlen(fc) & 3` bytes after the MAC header to 4-byte-align the payload (2 B for a 26-B
QoS header, 0 for 24-B mgmt/non-QoS), but the over-air FCS excludes them. CRC over the padded frame
fails for every QoS frame — which is all downlink-unicast data and all four EAPOL M1-M4. Strip the
pad before the FCS check (`_strip_alignment_padding`, mirrors `ath9k_rx_skb_postprocess`).

**Monitor promiscuity rides entirely on the PROM bit in `AR_RX_FILTER`** (`0xC03F`), and the
firmware clears the filter on every reset/channel-change — so `_apply_monitor_rx_filter` must
re-write it after connect AND after every `set_channel`. The BSSID mask is all-ones (exact-match),
not a zero mask; PROM, not the mask, is what makes it promiscuous.

**PROM is only partially effective on this cleanroom FW.** Locked on one AP's channel it passes
uplink unicast (RA=BSSID) and frames addressed to other BSSIDs, but downlink-unicast
(RA=an-individual-client) was never observed. Whether that's an RX-path bug or the cleanroom FW/PHY
never handing it up is unresolved; the DEBUG-gated `[RXGATE]` tally in `parse_rx_frame` classifies
each frame by direction and which gate dropped it, to settle this on hardware.

**Single bulk-IN reader only.** Parallel `dev.read()` on EP `0x82` delivers URBs out of order in
PyUSB's sync model — earlier 4-reader attempts produced ~40% FCS-corrupt frames. Real multi-URB
pressure would need a libusb1 async port (also noted for MT7921AU in `docs/porting/METHODOLOGY.md`).

**The RX-poll reader-thread port is unnecessary here** (HW-measured). ath9k's two independent
read-tasks (Control + Data EP) keep reads in flight even when the event loop is starved, unlike the
single-loop Realtek pattern — under a synthetic loop hog RX did not drop.

## Orientation

Soft-MAC chip: firmware does HTC/WMI, the host drives PHY/MAC register writes. RX comes up the HIF
stream on bulk EP `0x82` (wrapped `[len][tag=0x4e00][HTC frame][pad]`, chunks span transfers);
`transport._handle_bulk_in` mirrors the kernel `ath9k_hif_usb_rx_stream` reassembler.
`parse_rx_frame` runs the acceptance gate (length → magic `80 16 80 80 01 FF` → rs_status → declared
length → strip pad → FCS). TX inject goes to bulk EP `0x01` with the HIF/HTC/`tx_mgmt_hdr` wrap —
see `AthMetadataLayer.pack_tx_mgmt`. Channel lock is one synth word to `AR_PHY_SYNTH_CONTROL`
(`0x9874`) via `WMI_REG_WRITE`; see `sequences/tuning.py:_synth_word`. Calibration is offloaded to a
background thread (~1,094 WMI commands, ~1 s) so it doesn't freeze the UI loop. WMI is stop-and-wait
over a 1-slot mailbox, resent on timeout to recover from desynced USB toggle bits.

Names match the kernel; cross-reference `data_dumps/ath9k-source-v6.18/` (`hif_usb.c`,
`htc_drv_txrx.c`, `mac.h`).

## Debug log

### 2026-05-25 — QoS padding silently dropped the whole 4-way

Scanning worked but no 4-way ever captured in-app. Beacons/non-QoS use a 24-B header (pad=0) so they
passed; every QoS frame (downlink-unicast data + all EAPOL M1-M4, which are QoS) ran CRC32 over the
2 padding bytes and failed the FCS gate, dropped silently. Fix: strip `hdrlen & 3` pad before FCS +
parse. HW-confirmed M1-M4 captured warm and cold. Refuted along the way: parse mis-alignment (a
`[EAPOL-MISPARSE?]` probe stayed silent — EAPOL was failing FCS upstream, not mis-decoding) and
RX-filter/BSSID-mask config (checked against the airmon-ng pcap ground truth; our `0xC03F` write is
byte-identical to the kernel monitor recipe). Don't re-chase RX-filter/poll/parse — settled.

### 2026-05-25 — cold-boot PMKID hung; warm worked

Root cause was DATA-endpoint credit starvation, not toggle bits (so `reset_pipes()` was no fix).
`inject_frame` blocks on a credit for EP 5; the device only replenishes an endpoint after the host
consumes one, and HTC READY grants initial credits to EP 1/2 only — so EP 5 sat at 0 forever cold.
RX uses no credits, hence fine. Fix: seed `data_endpoint_id` credits at the end of cold connect,
mirroring the warm path. User confirmed cold PMKID works first-try.

### 2026-06-21 — channel-tune was a 2-channel stub

`set_channel` shipped `SYNTH_WORDS` for CH1 + CH6 only, silently pinning every other channel to CH6
— a card-wrecking bug found live. Fixed with the ath9k fractional-N synth formula (reproduces both
captured words). Per-channel analog/NF/IQ calibration writes remain unported; treat any other "RX
basically works" stub as suspect until audited against `ath9k_htc`.

### 2026-06-05 — phantom "5 GHz" APs in the soak report

The 30-min soak report listed a few 5 GHz APs though the radio only hopped 1-13. They're corrupted
beacons whose DS-Param channel byte bit-flipped to ≥36 (the diag bands an AP by its advertised
channel) — same noise class as the ~2.7% garbage OUIs, not actual 5 GHz reception.
