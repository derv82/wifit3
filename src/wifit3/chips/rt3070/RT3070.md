# RT3070 (ALFA AWUS036NH)

A clean-room port of the rt2x00 kernel driver (`rt2800usb.c` / `rt2800lib.c` / `rt2x00usb.c`,
v6.18), decoded off this card's own cold-boot capture. RT3070F silicon (rev `0x0201`), RF3020,
1T1R, 2.4 GHz only. Standalone `chips/rt3070/` — deliberately anti-DRY; it does **not** share the
`chips/rt2800usb/` base (see Gotchas).

## Status

- Cold init, firmware boot, channel hop: byte-perfect on the wire — `verify_pcap.py rt3070` passes
  all 8879 control ops of capture-1 (cold bring-up + the full operational phase), waiving only the
  678 `TX_STA_FIFO` polls aireplay fires during human-fired deauth (bulk-OUT TX is out of the
  control gate by design).
- Monitor RX: working on hardware, kernel-parity — `beacon_watch.py` measured 8.4 beacons/s on the
  best AP (live, ch1, 12 s) vs 8.9/s for the kernel's own fixed-ch1 segment of capture-1.
- Live TX: confirmed on hardware (human-fired) — a byte-matched deauth dropped a real client and
  yielded its reconnect handshake (39 EAPOL frames over 30 s).
- Warm reattach: working — a re-run without a replug reads `PBF_SYS_CTRL` (READY set + pre-init
  bit 13 clear) and skips FW + init + monitor entry, resuming RX.
- Multi-chain (RT3071/3072/3090, 2T2R) branches are ported but `#TODO untestable` — no hardware.
- EEPROM-variant general: runs on ANY 148f:3070 regardless of EEPROM. The RF companion is
  resolved from `NIC_CONF0.RF_TYPE` (`eeprom.resolve_rf_chip`); an unburned/mislabeled RF (one
  outside the ported rf3xxx set) is tuned on the RT30xx silicon default + logged as an untested
  variant rather than `-ENODEV`'d. SW antenna diversity (EEPROM `ANT_DIVERSITY`) is ported. The
  RF3020/1T1R/no-diversity reference stays byte-identical (`verify_pcap` capture-1 PASS).

## Gotchas

**Don't copy `chips/rt2800usb/eeprom.py` — it has a confirmed EFUSE addressing bug.** The kernel
`rt2800_read_eeprom_efuse` walks a u16 **word** offset (`for i ... i += 8`, `EFUSE_CTRL_ADDRESS_IN
= i` in words); the shared base loops `range(0, 512, 16)` and sets `ADDRESS_IN = byte offset`, so
from block 1 on it fetches from double the address. Block 0 (MAC) is correct, which is why nobody
noticed. Our reader passes the word offset; the gate catches the wrong one on the 2nd block. The
shared bug is filed in `chips/rt2800usb/RT2800USB.md` for a future family-perfection pass.

**Firmware is the *first* 4 KB of `rt2870.bin`, not the second.** The kernel selects `offset=0`
for RT2860/RT2872/RT3070; `offset=4096` is for everyone else — and that 2nd half is actually
`rt5572.bin`, a different card. Shipped as `assets/rt3070_fw.bin` (md5
`d94f0280cf9980999dbc2b999b281edb`), byte-verified against the wire's multiwrite to `0x3000`.

**This card's EFUSE is factory-burned (real MAC, real freq trim), not the blank counterfeit case.**
The driver reads + parses the EFUSE at runtime and branches on what it finds — nothing is
hardcoded. `validate_eeprom` (ported from `rt2800_validate_eeprom`) fills defaults for blank fields
on the in-RAM image only; it's a no-op on this card, exercised only by a blank/counterfeit EFUSE.

**Sustained-use RX falloff was concurrency, not AGC.** A symptom that read like sensitivity drift
(8–10/s decaying to ~2/s, only a fresh bring-up recovers) was actually an RX-DMA wedge from two
control transfers colliding — fixed by serializing device ops under `_hw_lock`. The STA-only
`link_tuner` never running in monitor mode is per-kernel-correct and *not* a degradation cause.

**The link tuner emits nothing in this capture.** It's gated on `intf_sta_count`, which a
monitor-only interface never increments, so the ~1 Hz worker never schedules. The BBP66 AGC writes
on the wire are `reset_tuner` (default VGC), run on every channel config. `config_erp` is likewise
BSS-change driven — ported for a future STA port, not called here.

**Family wire-format scars** (re-derived from source, confirmed on this wire — the EFUSE bug proves
our code can be wrong, so trust the wire): RX needs L2-pad removal before FCS trim and frames are
FCS-stripped before the callback; TX needs the +4 USB end-pad, `QSEL=2`, bulk-OUT EP `0x02`, and
`SHARED_KEY_MODE` cleared so injects aren't WEP-encrypted with a zero IV.

## Orientation

Start at `driver._bringup` for cold init order (probe → EFUSE → firmware → MAC/BBP/RFCSR → radio),
mirrored by the gate's `_walk_init`. EFUSE is `eeprom.read_eeprom_efuse` (word offset) + `parse_eeprom`;
every downstream write keys off the parsed fields (RF type, chains, freq_offset, ext-LNA) and the
`MAC_CSR0` chip rev. Channel tune is `chan.set_channel` → `config_channel_rf3xxx` (RF3020); monitor
entry is `monitor.enable_monitor` (`config_filter` → `0x93`). RX decode is `rx.iter_frames`; TX desc
build is in `tx.py` (wired + pcap-verified, fired only by the human). Names match the kernel C — grep
`driver_sources/rt2x00-source-v6.18/` to cross-reference.

RT3070F rev gating: the `LDO_CFG0` BGSEL/VLEVEL write, the RT3071/3090 branch, and the trailing
`RFCSR27=0x03` are all correctly skipped on this rev; ported `#TODO untestable`.

## Debug log

### 2026-07-11 — EEPROM-variant generalization (RF companion + antenna diversity)

Sibling pass to the rt2800usb generalization (`ce8f3ef`). Two runtime-EEPROM branches were
fail-loud (`raise NotImplementedError`); both now gate on the EEPROM so a non-reference
148f:3070 comes up instead of crashing, with the RF3020 reference byte-identical:

- **`chan.config_channel`** — was `if rf_type in _RF3XXX … else raise`. RT3070/3071/3090 silicon
  only ever tunes via `config_channel_rf3xxx` (the radios it ships: RF2020/3020/3021/3022/3320),
  so the dispatch collapses to that one call: any RF (incl. an unburned/mislabeled `RF_TYPE`, or
  the kernel's rf3052/rf3053/rf3322/rf55xx radios this driver doesn't claim) runs the silicon
  default. `eeprom.resolve_rf_chip` names it + flags `ported`; `driver._bringup` logs the config
  once and warns on an untested variant. **Landmine avoided:** the reference's `EEPROM_CHIP_ID`
  (word0) reads `0x3070`; resolving RF from it would wrongly pick RF3070→`config_channel_rf53xx`.
  RT3070 silicon resolves RF from `NIC_CONF0.RF_TYPE` (`0x05`=RF3020) [SRC rt2800lib.c:11187-11201].
- **`chan._set_ant_diversity`** — ported 1:1 from `rt2800_set_ant_diversity` [SRC rt2800lib.c:2300]:
  USB `MCU_ANT_SELECT` eesk pin + `GPIO_CTRL` DIR3/VAL3, reached only for a 1-chain RT3070/RT3090
  with `ANT_DIVERSITY` set (`default_ant.rx`: div 1/2→ANTENNA_A, 3→ANTENNA_B). Reference is
  `ANT_DIVERSITY=0` ⇒ never called. The PCI `E2PROM_CSR` arm is a different bus, omitted.

Antenna chain-count paths (`config_ant`, `config_channel_rf3xxx` RFCSR1 PD bits, TX_PIN PA/LNA)
were already runtime-gated on `tx/rx_chain_num`. Gates: `verify_pcap` capture-1 8879/8879 PASS,
`pytest tests/chips/rt3070` 11 passed, ruff clean.

**Residuals (not ported — genuinely different silicon/radio, out of scope for 148f:3070):** the
non-rf3xxx `config_channel` arms (rf3052/rf3053/rf3322/rf55xx for RF3052/RF3053/RF3322/RF5592) and
the RT5390/5392/3290/6352 `EEPROM_CHIP_ID` RF-resolution + RT3352/3883/5350/5592 hardcodes — those
belong to silicon this driver does not claim (adding them = a new chipset). An RF_TYPE that maps to
one of them still gets the rf3xxx give-it-a-shot tune + the untested-variant warning.

### 2026-06-09 — autonomous port to complete

Ported clean-room from the kernel C against capture-1, milestone by milestone, with `verify_pcap`
as both unit test and compass (first unaccounted op = next thing to port). Whole capture reproduces
byte-perfect: cold bring-up through the operational phase (airmon monitor entry, every airodump/iw
hop). ch1 tune byte-matches — `rfcsr12=0x66` (`default_power1` decoded from EEPROM TXPOWER_BG1),
`rfcsr23=0x0a` (freq_offset 10), `rfcsr24/31=0x08` (calibration_bw20, threaded out of the M2f
rx-filter calibration). TX_PWR_CFG_0..4 reproduce the byrate table with delta 0.

Live TX later confirmed by the human: `tx.py` descriptor (QSEL=2, +4 end pad, TX_OP=HT_NONE, WIV=1)
+ byte-matched deauth (duration `0x013a`, per-frame incrementing seqctl — a constant-seq bug would
let a receiver's duplicate filter drop every deauth after the first) dropped a real client and
captured the reconnect handshake.

### 2026-06-09 — RX falloff root cause

Extended-TUI RX decay looked like AGC drift but was an RX-DMA wedge: a UI view switch cancels a
channel-hop mid-`set_channel`; the asyncio lock releases on `CancelledError` but the
`run_in_executor` thread keeps running `config_channel`, so the next tune spawns a second thread and
two control transfers collide → `WPDMA_GLO_CFG`→0 (control alive, RX dead; only re-init recovers,
hence a retune not helping). Fixed by serializing device ops under `threading.Lock` (`_hw_lock`) +
a no-hardware concurrency regression test.
