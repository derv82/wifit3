# RTL8187L — Ground-Truth Doc

## Potential Known Gaps

Cross-driver gap classes (project audit 2026-05-25).

- [x] **RX polling loop** — RX reads + dispatch run on the shared `RxReaderThread`
  (`driver.py` `_rx_read_once`/`_rx_dispatch`), off the event loop, so parsing never
  starves the next read. HW-verified by the 2026-05-31 handshake/WEP runs.
  - **Read DEPTH is NOT the bottleneck** (measured 2026-06-12): a multi-reader pool (8/16
    concurrent bulk reads, the kernel's 32-URB approach) gave **no** improvement over the
    single read — the raw cold loop already hits 215–323 frames/s with **zero empty reads**
    (the chip delivers as fast as we read; concurrent reads drain the *same* FIFO, not
    faster). Don't rebuild the pool. The weak-RX symptom was the warm-path dead radio
    (below), not read depth.
- [x] **RX filter / monitor mode (ToDS capture)** — HANDLED, now **byte-for-byte**.
  `mac.start()` writes the station RX_CONF baseline (`0x9094FC0A`, no monitor); a separate
  `mac.configure_filter()` enters monitor with `0x909CFC0B = baseline | RX_CONF_MONITOR (bit 0)
  | RX_CONF_CTRL (bit 19)` — exactly what airmon requests (FIF_OTHER_BSS|FIF_CONTROL) and what
  the capture shows. MONITOR makes the chip accept all BSSIDs incl. client→AP (ToDS EAPOL). The
  earlier inline-in-`start()` single write was the monitor-deviation playbook's seed case — and
  it was the deviation (wrong order + missing CTRL); the byte-for-byte push fixed it.

Realtek 802.11g USB chipset (rtl818x family — older, pre-rtw88). The
RTL8187L is a **hard-MAC** part: no firmware blob, no 8051 wlan CPU.
All bring-up is plain vendor control transfers.

Every fact below is either:
- **[SRC]** a direct citation from `data_dumps/rtl818x-source-v6.18/`, or
- **[WIRE]** verified on real hardware via `scripts/rtl8187/test_hw_rtl8187.py`.

Anything *not* in this document is a hypothesis. Update as facts get
verified — do not let speculation accumulate here.

## Test hardware

- **Card**: ALFA AWUS036H
- **VID:PID**: `0bda:8187` [SRC `dev.c:49`, WIRE bus=2 in M1 hw test]
- **OUI**: `00:c0:ca` (ALFA Network) [WIRE M1 — `00:c0:ca:4e:ca:e0`]
- **USB**: 2.0 high-speed (`bcdUSB=0x0200`) [WIRE M1]
- **HWVER**: `RTL8187vB` (TX_CONF[27:25] = 4, the "vB default" branch of
  the kernel switch) [WIRE M1 — `TX_CONF=0x18000000`]
- **RF silicon**: `RTL8225z2` (NOT the BCD rev) [WIRE M2c — RF reg 8 =
  `0x588`, RF reg 9 = `0x700` is the z2 signature]
- **asic_rev**: 1 → SPI uses the 8051 fast path (not the bit-bang
  fallback). 4× faster RF init than asic_rev=0 hardware.

Note: kernel `rtl8187_table[]` lists 21 different VID:PIDs that
dispatch to this driver. Wifit3 currently claims only `0bda:8187` —
other dongle vendors with the same silicon could be added trivially
(no code change beyond extending `SUPPORTED_IDS`).

## Hard-MAC means no firmware

No `request_firmware` anywhere in the kernel source [SRC grep across
`rtl8187/*.c`]. The chip's 8051 is in ROM, init is pure register pokes.
Compare to rtw88 (8821au/8822bu) where FW upload is ~106 ms of bulk-OUT
streaming.

This is also why ~9000 lines of replay sequences in the *old* wifit3
driver were unnecessary — the entire bring-up is ~300 register writes
plus ~700 RF SPI writes (mostly the rxgain table loops).

## Vendor control transfer protocol

[SRC `rtl8187.h:27-30`, `rtl8225.c:22-113`]

Every register access is a single `usb_control_msg`:

| Field           | Value                          |
|-----------------|--------------------------------|
| `bmRequestType` | `0xC0` (vendor IN) / `0x40` (vendor OUT) |
| `bRequest`      | `0x05` (REQ_GET_REG / REQ_SET_REG, same value) |
| `wValue`        | `0xFF00 + struct_offset` (see below) |
| `wIndex`        | `0..3` — page select; default 0 for `rtl818x_csr` regs |

**The 0xFF00 trick**: kernel does `priv->map = (struct rtl818x_csr *)0xFF00`,
so every named register's on-the-wire `wValue` is `0xFF00 + offset`. We
fold the base into our constants so callers never have to add it (see
`constants.py`). Examples:

| Register     | Offset | wValue |
|--------------|--------|--------|
| `MAC0`       | 0x00   | `0xFF00` |
| `CMD`        | 0x37   | `0xFF37` |
| `TX_CONF`    | 0x40   | `0xFF40` |
| `RX_CONF`    | 0x44   | `0xFF44` |
| `EEPROM_CMD` | 0x50   | `0xFF50` |
| `MSR`        | 0x58   | `0xFF58` |
| `RFPinsOutput` | 0x80 | `0xFF80` |
| `PHY[0..3]`  | 0x7C   | `0xFF7C..0xFF7F` |

**Magic registers**: a handful of bits live at `0xFExx` / `0xFFxx`
addresses that aren't inside `rtl818x_csr` (the reset toggle at
`0xFE18`, the USB-mode bit at `0xFE53`, the asic_rev word at `0xFFFE`).
These are addressed directly with the appropriate `wIndex` (1 for
page-1 regs).

## Bring-up flow (cold, ~3 seconds total)

```
connect()
  ├─ claim USB interface (set_configuration + claim_interface)
  ├─ probe()                ─ the kernel rtl8187_probe wire order (probe.py):
  │     ├─ eeprom_width      RX_CONF bit 6 → 93c46/93c66
  │     ├─ 93cx6 EEPROM      MAC (3 words) + TXPWR_CHAN_1/4 (ch 1..10) + TXPWR_BASE
  │     ├─ asic_rev          PGSELECT|1, read 0xFFFE (inside the EEPROM window)
  │     ├─ detect_chip_variant  TX_CONF[27:25] HWVER
  │     ├─ TXPWR_CHAN_6       EEPROM ch 11..14 (the !is_rtl8187b tail)
  │     ├─ detect_rf          RF probe regs 8+9 → BCD vs z2
  │     └─ rfkill init        is_radio_enabled (R GPIO0,W GPIO0,R GPIO1)
  │     → ProbeResult(mac, chip, RfSetup{asic_rev,variant}, TxPower{hw_value[14],base})
  ├─ is_chip_warm           ─ logged only; NOT trusted (RF dies on reopen — see below)
  ├─ cold_bring_up          ─ ALWAYS (no warm shortcut)
  │   ├─ init_hw
  │   │   ├─ set_anaparam(rfon=True)
  │   │   ├─ INT_MASK = 0; magic 0xFE18 reset toggle (10/11/00)
  │   │   ├─ cmd_reset    (CMD |= RESET, wait <20ms; EEPROM auto-load)
  │   │   ├─ set_anaparam(rfon=True)
  │   │   ├─ RF pin defaults, CONFIG1 = 0x80, BRSR = 0x01F3
  │   │   ├─ host_usb_init (FE53 |= 0x80, RFPinsOut/Sel/En = 0x80)
  │   │   ├─ RF_TIMING = 0x000A8008, RF_PARA = 0x00100044, CONFIG3 = 0x44
  │   │   ├─ priv->rf->init (build_rf_init binds the EEPROM TxPower):
  │   │   │     ├─ rtl8225_rf_init   (BCD)  → set_tx_power(ch1) from hw_value[0]
  │   │   │     └─ rtl8225z2_rf_init (z2)   → set_tx_power(ch1) from hw_value[0]
  │   │   └─ post-RF: PGSELECT|1 magic regs (0xFFFE=0x10, TALLY_SEL=0x80)
  │   ├─ start
  │   │   ├─ INT_MASK = 0xFFFF; MAR[0]=MAR[1]=0xFFFFFFFF
  │   │   ├─ RX_CONF = 0x9094FC0A  ← station baseline, NO monitor (dev.c:982-990)
  │   │   ├─ CW_CONF (clear per-pkt CW, set per-pkt retry)
  │   │   ├─ TX_AGC_CTL = 0 (no per-pkt gain/antsel)
  │   │   ├─ TX_CONF = CW_MIN | (7<<21 max_tx_dma) | NO_ICV
  │   │   └─ CMD |= TX_ENABLE | RX_ENABLE     ← chip is "live" here
  │   └─ configure_filter   ─ RX_CONF = 0x909CFC0B (baseline|MONITOR|CTRL); enter
  │                           monitor. Without MONITOR, ToDS DATA (incl. EAPOL) is
  │                           invisible. See [[feedback_station_vs_monitor_rcr]].
  ├─ probe_endpoints  ─ bulk_in=0x81, bulk_out=[0x02, 0x03]
  └─ start RX loop    ─ shared RxReaderThread polling bulk-IN
```

**M2c timing** [WIRE]: `cold_bring_up (with RF init) completed in 2.02s`
on the user's AWUS036H. Dominant cost is the 95-entry rxgain SPI loop
(190 RF writes) and the calibration sleeps (~700 ms of `msleep`).

## 93cx6 EEPROM (what `probe` reads)

[SRC `rtl8187.h:20-25`, `dev.c:1504-1528`, `eeprom_93cx6.c`]

The 8187L's MAC + per-channel TX power live in a 93cx6 SPI EEPROM, bit-banged through the
EEPROM_CMD register (`eeprom.py` ports the lib; the rtl8187 callbacks drive PROGRAM mode +
the 4 SPI lines). Width is 93c46 (6-bit addr) unless RX_CONF bit 6 is set. Word offsets:

| Offset | Field                | → channels |
|--------|----------------------|------------|
| 0x05   | `txpwr_base` (u16)   | folded into z2 TX power (cck `&0xF`, ofdm `>>4`) |
| 0x07   | MAC (3 words = 6 B)  | — |
| 0x16   | TXPWR_CHAN_1 (3 wds) | ch 1..6  (`hw_value` byte each) |
| 0x3D   | TXPWR_CHAN_4 (2 wds) | ch 7..10 |
| 0x1B   | TXPWR_CHAN_6 (2 wds) | ch 11..14 |

Each channel's `hw_value` packs `cck_power = hw_value & 0xF`, `ofdm_power = hw_value >> 4`
[SRC `rtl8225.c:626-627`]. **[WIRE] AWUS036H**: MAC `00:c0:ca:4e:ca:e0`, ch1 `hw_value=0x55`,
`txpwr_base=0x36` → z2 cck=min(5,15)+(0x36&0xF)=11, ofdm=(5+10)+(0x36>>4)=18 → `TX_GAIN_CCK=0x0b`,
`TX_GAIN_OFDM=0x12` — exactly the capture's hop writes. (The earlier zeros-stub wrote 0x00/0x03,
which is what diverged at the first hop until the EEPROM read landed.)

## RF dispatch (BCD vs z2)

The "RTL8225" name covers two silicon revisions with substantially
different init tables. Both ship under the same VID:PID — we have to
probe at runtime [SRC `rtl8225.c:1025-1044`]:

```
rtl8225_write(t, 0, 0x1B7)        # arm probe
reg8 = rtl8225_read(t, 8)
reg9 = rtl8225_read(t, 9)
rtl8225_write(t, 0, 0x0B7)        # restore
if reg8 == 0x588 and reg9 == 0x700:
    return RTL8225Z2
return RTL8225 (BCD)
```

[WIRE M2b/c]: user's AWUS036H reads `reg8=0x588 reg9=0x700` → z2. The
init tables differ in:

|                 | BCD (`rtl8225_rf_init`)    | z2 (`rtl8225z2_rf_init`) |
|-----------------|----------------------------|--------------------------|
| 16-entry RF init seq | 0x067, 0xFE0, ..., 0x914 | 0x2BF, 0xEE0, ..., 0x114 |
| rxgain table    | `rtl8225bcd_rxgain` (95)   | `rtl8225z2_rxgain` (95)  |
| gain table      | `rtl8225_gain` (28)        | `rtl8225z2_gain_bg` (21) |
| sensitivity row | 2 (-82 dBm)                | 3 (-78 dBm)              |
| OFDM PHY regs   | base values                | 7 entries diverge: 0x0a, 0x0d, 0x11, 0x1b, 0x1d, 0x21, 0x23, 0x25 |
| CCK PHY 0x44–0x4b | from `rtl8225bcd` table | from `rtl8225z2_tx_power_cck[0..7]` |
| TX-power setter | `rtl8225_rf_set_tx_power`  | `rtl8225z2_rf_set_tx_power` |

`build_rf_init(t)` returns the correct callable. `set_channel` uses the
cached `RfSetup` to dispatch the per-variant TX-power refresh.

## RX descriptor (rtl8187_rx_hdr, 16 bytes, trailing)

[SRC `rtl8187.h:44-51`]

Each bulk-IN URB carries one 802.11 frame with the 16-byte trailer
appended at the end:

```
[802.11 frame (FCS-inclusive)] [rtl8187_rx_hdr (16 bytes)]
```

Trailer layout:

| Offset | Type    | Field        | Notes |
|--------|---------|--------------|-------|
| 0      | u32 LE  | flags        | bits 0..11 = frame length; 13 = CRC32 err; 20..23 = rate idx; 25 = SPLCP |
| 4      | u8      | noise        | unused by RX path |
| 5      | u8      | signal       | bit 7 = antenna A(0)/B(1) |
| 6      | u8      | agc          | used for RSSI calc |
| 7      | u8      | reserved     | |
| 8      | u64 LE  | mac_time     | TSF timestamp at frame arrival |

**RSSI formula** [SRC `dev.c:354`]:
```
rssi_dbm = -4 - ((27 * agc) >> 6)
```
Range: agc=0 → -4 dBm; agc=255 → -111 dBm. Verified [WIRE M3] across
180 frames: min=-71, max=-40, mean=-55.4 — realistic 2.4 GHz values.

**FCS handling**: `RX_INCLUDES_FCS` is on, so the frame length in the
trailer includes the 4-byte FCS. Strip it before handing the MPDU to
the parser.

## TX descriptor (rtl8187_tx_hdr, 12 bytes, prepended)

[SRC `rtl8187.h:67-72`, `dev.c:247-285`]

```
[rtl8187_tx_hdr (12 bytes)] [802.11 frame]
```

Layout:

| Offset | Type    | Field         | Notes |
|--------|---------|---------------|-------|
| 0      | u32 LE  | flags         | bits 0..11 = frame length; 15 = NO_ENC; 17 = MOREFRAG; 18 = CTS; 23 = RTS; 19..22 = RTS rate; 24..27 = data rate |
| 4      | u16 LE  | rts_duration  | only for RTS/CTS frames |
| 6      | u16 LE  | len           | **kernel writes 0** — frame length is in `flags`, this is alignment padding |
| 8      | u32 LE  | retry         | `(retry_count - 1) << 8`. Default `RETRY_COUNT=7` → `0x0600` |

**Bulk-OUT EP**: 0x02. (Device also exposes 0x03 but kernel only uses
0x02 for the L-branch; 0x03 is for the 8187B 4-queue split.)

**URB_ZERO_PACKET** [SRC `dev.c:315`]: the kernel sets it on every TX URB; libusb appends a
terminating zero-length packet only when the transfer is an exact multiple of the 512-byte
bulk-OUT wMaxPacketSize. PyUSB's `dev.write` does NOT — so a frame whose total length is a
512-multiple has no trailing short packet to signal end-of-transfer and the chip stalls
instead of firing it. `tx.inject_frame` sends an explicit ZLP in that case
(`sent % 512 == 0`). Small frames (deauth = 38 B) are unaffected.

**Sequence numbers are stamped in software** [SRC `dev.c:270-275`]: the 8187**L** has no
hardware sequence assignment — the `TX_CONF_HW_SEQNUM` bit (1<<30) is set only on the 8187**B**
path. The kernel L-path stamps `seq_ctrl` itself (`priv->seqno += 0x10` per first fragment).
The wider wifit3 stack assumes the chip auto-assigns seq (Ralink `NEW_SEQ`, rtw88 auto-seq), so
without this every injected frame leaves `seq=0`; the driver's `inject_frame` calls
`tx.stamp_seq_ctrl` to advance the seq per frame (preserving fragment bits). Single frames
(deauth) and ARP replays (captured seq) didn't care, but a multi-frame association+EAPOL
exchange (PMKID extraction, WPS) was deduped by the AP as retransmissions until this landed.
Matches the captured aireplay deauths (seq 0x0000, 0x0010, 0x0020, …). An 8187B port would set
`HW_SEQNUM` instead and skip the software stamp.

**M5 verification** [WIRE]: 20-byte tx_hdr for a 26-byte deauth =
`1a8000000000000000060000`, decoded:
- `flags = 0x0000801a` = NO_ENC | length 26
- `rts_duration = 0`
- `len = 0`
- `retry = 0x00000600` = (7-1)<<8

20 deauths sent at 1 Mbps CCK, 0 USB errors, RX continued at 36
frames/sec in parallel.

**TX byte-diff vs the captured aireplay deauth** [WIRE 2026-06-11] (Post-Port checklist): our
`build_tx_hdr(retry_count=1)` (the `use_no_ack=True` path) reproduces aireplay's deauth tx_hdr
**byte-for-byte** — `1a8000000000000000000000` (retry=0, no-ACK). The deauth body matches on
FC / addr1 / addr2 / addr3 / reason; only **seqctl** (per-send, legitimate) and **duration**
differ — ours is `0x0000`, the kernel/aireplay computes `0x013a` (314 µs = SIFS + a 1 Mbps ACK,
the NAV for the unicast ACK it expects). The duration=0 is a **pre-existing** `build_deauth`
nuance (untouched by the byte-for-byte push, which was the bring-up/control path) — deauth still
lands, but a correct injector would set the unicast NAV. Flagged for a TX follow-up; not a
bring-up gap.

## Channel tune

`chan.config_channel` ports the whole `rtl8187_config` [SRC `dev.c:1155-1179`], not just the
inner `rtl8225_rf_set_channel` [SRC `rtl8225.c:986-1002`]. The synth retune is bracketed by a
TX_CONF MAC-loopback window (the kernel comment: TX during a channel change "causes problems
and the card will stop work until next reset") and followed by the ATIM/beacon writes:

1. `reg = read32(TX_CONF)` — **read back**: the base carries read-only HWVER bits (0x98e80000
   on the AWUS036H), so this is a real RMW the gate serves, never a hardcoded value.
2. `write32(TX_CONF, reg | LOOPBACK_MAC)` — loopback on.
3. `set_chan`: per-variant `set_tx_power(channel)` (from the EEPROM `TxPower`) + the single
   RF7 synth write `rtl8225_write(0x7, rtl8225_chan[channel-1])` + `msleep(10)` PLL settle.
4. `write32(TX_CONF, reg)` — loopback off.
5. `ATIM_WND=2`, `ATIMTR_INTERVAL=100`, `BEACON_INTERVAL=100`, `BEACON_INTERVAL_TIME=100`.

Per-channel synthesizer word from the shared `rtl8225_chan[]` table (used by both BCD and z2):

```python
rtl8225_chan = (
    0x085c, 0x08dc, 0x095c, 0x09dc, 0x0a5c, 0x0adc, 0x0b5c,   # ch 1..7
    0x0bdc, 0x0c5c, 0x0cdc, 0x0d5c, 0x0ddc, 0x0e5c, 0x0f72,   # ch 8..14
)
```

**M4 verification** [WIRE]: hops across 1, 6, 11, 13 deliver different
BSSID sets per channel (13/10/15/3 unique BSSIDs respectively), proving
the synth actually moves. RF7 for ch 13 = `0x0e5c` matches table
exactly.

## No warm reattach — always cold (the radio doesn't survive a reopen)

**There is no warm fast-path; `connect()` always runs the full cold bring-up.** The earlier
warm-reattach optimisation (skip the ~2 s cold init, just re-arm via `start()` +
`configure_filter`) was **removed** — it ran a dead radio.

`is_chip_warm(t)` (True iff `CMD & (TX_ENABLE|RX_ENABLE)`) is **not trustworthy as a "RF is
healthy" signal on this chip.** The 8187L's RF/PHY/AGC state does **not** survive a USB handle
close + reopen: the next `set_configuration` soft-resets the radio, yet the CMD TX/RX-enable
bits persist. So a reattached chip reports "warm" while its AGC is dead — **agc=0 in every RX
descriptor → RSSI pinned at −4 dBm, gain control off, ~3× fewer frames, weak EAPOL/handshake
capture.** Re-arming with `start()` alone (no RF init) never reprograms it.

`[HW]` 2026-06-12 (AWUS036H, raw instrumented RX, ch1): **cold 215–323 frames/s, RSSI
−72…−10 (mean −34), 0 % FCS err** vs **warm 31–67 frames/s, RSSI all −4 (agc=0)**. The RF init
(`rtl8225z2_rf_init`) **is** the ~2 s cost the warm path tried to skip (the 95-entry rxgain SPI
loop + cal sleeps), so once you concede the RF must be reprogrammed there is no warm saving
left — always-cold is both correct and as fast as any working path. (A future micro-opt could
re-write only the AGC/PHY tables and skip the rxgain loop *if* the reopen turns out to nuke only
part of the RF state — unverified, not worth it for a ~2 s reconnect.)

> The earlier `[HW] warm 7.8 beacons/s` "verification" was wrong: it watched only the
> ceiling-capped strongest AP (~9.77/s max), which looks fine even on a dead-gain receiver. RX
> health must be measured by **total frames/s + RSSI spread**, not one AP's beacon rate.

If you see `cmd_reset: ... never cleared (timeout)` on hw, replug and retry.

## Byte-for-byte push — COMPLETE (2026-06-11)

The full bring-up now reproduces the cold-boot capture **single-cursor, byte-for-byte**:
`scripts/rtl8187/verify_pcap.py` walks all **9,845 control ops** of
`usb_dumps_new/captures_rtl8187/capture-1` — probe → init_hw → rtl8225z2 RF init (8051 fast
path) → start → configure_filter → every airodump/iw hop — with the periodic rfkill poll and
the per-hop monitor-filter reapply dispatched as async producers. The **only** waiver is the
191 aireplay-triggered TX-status reads (`rtl8187_work`, reg 0xFFFA) at the capture tail — a
different program's TX consequence (bulk-OUT is out of the control gate). **Init + airmon
entry reproduce with ZERO waivers.**

The gate replays at the `ctrl_transfer` layer (`rtw88_pcap_replay.ReplayDevice` +
`extract_ctrl_ops`, urb-id paired) so the REAL `transport.py` drives it — the rtl8225 8051 RF
SPI (`t.dev.ctrl_transfer` wIndex=0x8225) and the EEPROM_CMD bit-bang replay with zero
reimplementation. That was the stated blocker; solved.

What the push moved from stub/hypothesis to byte-for-byte (all gate-confirmed):

1. **93cx6 EEPROM read** (`eeprom.py`, `probe.py`). The kernel probe bit-bangs the EEPROM for
   the MAC + per-channel TX power + `txpwr_base` before init_hw, and the per-channel `hw_value`
   feeds every `set_tx_power`. It was stubbed to zeros — which is why the **RF init's own
   `set_tx_power(channel 1)` diverged at the first hop** (`TX_GAIN_CCK` wrote 0x00; wire wants
   0x0b). AWUS036H: ch1 `hw_value=0x55`, `txpwr_base=0x36` → cck=min(5,15)+(0x36&0xF)=**11**,
   ofdm=(5+10)+(0x36>>4)=**18** → `TX_GAIN_CCK=0x0b` / `TX_GAIN_OFDM=0x12`, matching the wire.
2. **Monitor RX_CONF is a SEPARATE write — the hypothesis was CONFIRMED; the old port was
   wrong.** `mac.start()` writes the kernel's station baseline `0x9094FC0A` (NO monitor bit,
   dev.c:982-990); `mac.configure_filter()` then enters monitor with
   `0x909CFC0B = baseline | MONITOR | CTRL` (dev.c:1338, `iowrite32_async`). The earlier port
   folded monitor into `start()` as one `0x9094FC0B` write — wrong order AND it **dropped the
   CTRL bit** (0x80000) airmon also requests (FIF_CONTROL). mac80211 reapplies the monitor
   RX_CONF on every hop.
3. **`config_channel` = the whole `rtl8187_config`** — the synth tune is bracketed by a TX_CONF
   `LOOPBACK_MAC` window (RMW: the base carries read-only HWVER bits, so it is read back, not
   assumed) and followed by the ATIM/beacon interval writes. Was just the synth + set_tx_power.
4. **rfkill GPIO poll** (`rfkill.py`) — `rtl8187_is_radio_enabled` (R GPIO0, W GPIO0, R GPIO1)
   fires every ~1.3-1.8 s; dispatched in the operational walk as an async producer.

Removed the divergent standalone `probe_asic_rev`/`probe_rf_setup` (asic_rev is now read
inside `probe()`'s single EEPROM_CMD window, matching the kernel — no second code path to drift).

`[HW]` 2026-06-11, AWUS036H:
- **Cold path** (`test_hw --phase channel`, forced cold bring-up + RF init with EEPROM TX
  power): clean sweep ch1=71 beacons/9 APs, ch6=30/8, ch11=147/17, ch13=15/2; RSSI −52…−63 dBm;
  distinct BSSID sets per channel (synth moves). The calibrated TX power did not hurt RX.
- **Warm path** — REMOVED (2026-06-12). The earlier "warm 7.8 beacons/s" was a measurement
  artefact (ceiling-capped best AP); the warm radio is actually dead (agc=0). See
  "No warm reattach" below. `connect()` now always cold-inits.
- **30-min soak** (`sweep.py --skip-baseline --longrun-min 30 --hop-interval 0.25`, ~7200
  `config_channel` hops under load): **stable — no degradation, no wedge.** Ran the full
  1800 s; active-BSSID trend flat (median of first-3 vs last-3 60 s buckets 25 → 24, ratio
  0.96); 21–29 APs and 790–1447 frames every bucket; zero dead windows. The sweep's two WARNs
  (OUI-garbage ~14%, DS-IE-vs-current-tune mismatch ~42%) are environmental, not regressions —
  weak-frame bit errors + 2.4 GHz adjacent-channel overlap at a 0.25 s hop, which any driver
  shows in this environment.

## WPS verdict (2026-06-11)

WPS (❌ in VERIFICATION.md) is **out of the driver's port scope** — not a bring-up bug.
The driver supplies exactly the primitives the WSC Registrar needs, both `[HW]`-confirmed:
`inject_frame` (TX — M5 deauth) and the EAPOL/EAP RX callback (Handshake + PMKID green). A live
WPS run is **agent-prohibited** (it injects EAPOL-Start/M2/M4 — live 802.11 TX, the user's gate
[[passive_by_default]]). The ❌ therefore lives in the WSC engine: the from-scratch Python
Registrar (`engine/attacks/wps/`) and the hard-MAC ACK/retransmit semantics bully relies on
(no firmware → userland owns retransmit) — tracked in `engine/attacks/wps/README.md`, not here.
Confirm with a user-fired PIN/PBC attempt.

**Capture coverage** (Post-Port item 3): the gate PASSes full single-cursor against **all four
captures** of this card — `usb_dumps_new/captures_rtl8187/capture-1` (9,845 ops) AND the three
older sessions `usb_dumps/captures_rtl8187/capture-1..3` (7,522 / 7,528 / 7,520 ops). All four
reproduce the identical probe (same EEPROM: mac `00:c0:ca:4e:ca:e0`, ch1 `0x55`, base `0x36`) +
init/RF/start/monitor (5,171 ops) + every hop; only the per-session aireplay TX-status reads
(64–191) are waived. Pass an explicit path: `verify_pcap.py usb_dumps/captures_rtl8187/capture-2.pcap`.

Rules still in force: hard-MAC = no firmware; 20 MHz only; agent never fires live TX (wire it,
user fires); don't touch VERIFICATION.md/README.md autonomously (PORTING.md).

## Hardware test cheat sheet

```
# M1 — control transfers + ID probe (no bring-up)
uv run python scripts/rtl8187/test_hw_rtl8187.py --phase open

# M2a — MAC bring-up only (no RF; receiver blind, FIFO primed)
uv run python scripts/rtl8187/test_hw_rtl8187.py --phase init

# M2b/c — full RF init (BCD or z2 auto-detected) + bulk-IN drain
uv run python scripts/rtl8187/test_hw_rtl8187.py --phase rf

# M3 — decode 3s of frames, print type/RSSI/BSSID stats
uv run python scripts/rtl8187/test_hw_rtl8187.py --phase rx

# M4 — hop ch 1/6/11/13, count per-channel beacons
uv run python scripts/rtl8187/test_hw_rtl8187.py --phase channel

# M5 — fire 20 broadcast deauths at the strongest ch11 BSSID
uv run python scripts/rtl8187/test_hw_rtl8187.py --phase tx

# M6 — listen for EAPOL frames on a chosen channel for ~30s
uv run python scripts/rtl8187/test_hw_rtl8187.py --phase handshake --channel 11
```

Each phase strictly supersedes the previous ones (don't chain back to
back — they all run `cold_bring_up` at the start).
