# RTL8187L — Ground-Truth Doc

## Potential Known Gaps

Cross-driver gap classes (project audit 2026-05-25).

- [x] **RX polling loop** — RX reads + dispatch run on the shared `RxReaderThread`
  (`driver.py` `_rx_read_once`/`_rx_dispatch`), off the event loop, so parsing never
  starves the next read. HW-verified by the 2026-05-31 handshake/WEP runs.
- [x] **RX filter / monitor mode (ToDS capture)** — ALREADY HANDLED (offline
  verdict). `mac.py:341-353` sets `REG_RX_CONF` with **RX_CONF_MONITOR (bit 0)**
  ("critical for EAPOL visibility") + MGMT|DATA|BSSID|BROADCAST|NICMAC. Monitor
  bit makes the chip accept all frames incl. client→AP (ToDS). This is the
  original case that seeded the monitor-deviation playbook.

Realtek 802.11g USB chipset (rtl818x family — older, pre-rtw88). The
RTL8187L is a **hard-MAC** part: no firmware blob, no 8051 wlan CPU.
All bring-up is plain vendor control transfers.

Every fact below is either:
- **[SRC]** a direct citation from `data_dumps/rtl818x-source-v6.18/`, or
- **[WIRE]** verified on real hardware via `scripts/rtl8187/test_hw_rtl8187.py`.

Anything *not* in this document is a hypothesis. Update as facts get
verified — do not let speculation accumulate here.

## Test hardware

- **Card**: ALFA AWUS036H
- **VID:PID**: `0bda:8187` [SRC `dev.c:49`, WIRE bus=2 in M1 hw test]
- **OUI**: `00:c0:ca` (ALFA Network) [WIRE M1 — `00:c0:ca:4e:ca:e0`]
- **USB**: 2.0 high-speed (`bcdUSB=0x0200`) [WIRE M1]
- **HWVER**: `RTL8187vB` (TX_CONF[27:25] = 4, the "vB default" branch of
  the kernel switch) [WIRE M1 — `TX_CONF=0x18000000`]
- **RF silicon**: `RTL8225z2` (NOT the BCD rev) [WIRE M2c — RF reg 8 =
  `0x588`, RF reg 9 = `0x700` is the z2 signature]
- **asic_rev**: 1 → SPI uses the 8051 fast path (not the bit-bang
  fallback). 4× faster RF init than asic_rev=0 hardware.

Note: kernel `rtl8187_table[]` lists 21 different VID:PIDs that
dispatch to this driver. Wifit3 currently claims only `0bda:8187` —
other dongle vendors with the same silicon could be added trivially
(no code change beyond extending `SUPPORTED_IDS`).

## Hard-MAC means no firmware

No `request_firmware` anywhere in the kernel source [SRC grep across
`rtl8187/*.c`]. The chip's 8051 is in ROM, init is pure register pokes.
Compare to rtw88 (8821au/8822bu) where FW upload is ~106 ms of bulk-OUT
streaming.

This is also why ~9000 lines of replay sequences in the *old* wifit3
driver were unnecessary — the entire bring-up is ~300 register writes
plus ~700 RF SPI writes (mostly the rxgain table loops).

## Vendor control transfer protocol

[SRC `rtl8187.h:27-30`, `rtl8225.c:22-113`]

Every register access is a single `usb_control_msg`:

| Field           | Value                          |
|-----------------|--------------------------------|
| `bmRequestType` | `0xC0` (vendor IN) / `0x40` (vendor OUT) |
| `bRequest`      | `0x05` (REQ_GET_REG / REQ_SET_REG, same value) |
| `wValue`        | `0xFF00 + struct_offset` (see below) |
| `wIndex`        | `0..3` — page select; default 0 for `rtl818x_csr` regs |

**The 0xFF00 trick**: kernel does `priv->map = (struct rtl818x_csr *)0xFF00`,
so every named register's on-the-wire `wValue` is `0xFF00 + offset`. We
fold the base into our constants so callers never have to add it (see
`constants.py`). Examples:

| Register     | Offset | wValue |
|--------------|--------|--------|
| `MAC0`       | 0x00   | `0xFF00` |
| `CMD`        | 0x37   | `0xFF37` |
| `TX_CONF`    | 0x40   | `0xFF40` |
| `RX_CONF`    | 0x44   | `0xFF44` |
| `EEPROM_CMD` | 0x50   | `0xFF50` |
| `MSR`        | 0x58   | `0xFF58` |
| `RFPinsOutput` | 0x80 | `0xFF80` |
| `PHY[0..3]`  | 0x7C   | `0xFF7C..0xFF7F` |

**Magic registers**: a handful of bits live at `0xFExx` / `0xFFxx`
addresses that aren't inside `rtl818x_csr` (the reset toggle at
`0xFE18`, the USB-mode bit at `0xFE53`, the asic_rev word at `0xFFFE`).
These are addressed directly with the appropriate `wIndex` (1 for
page-1 regs).

## Bring-up flow (cold, ~3 seconds total)

```
connect()
  ├─ claim USB interface (set_configuration + claim_interface)
  ├─ detect_chip_variant   ─ TX_CONF[27:25] HWVER probe              [M1]
  ├─ read_perm_mac         ─ MAC0..5 read                            [M1]
  ├─ is_chip_warm          ─ CMD has TX_ENABLE|RX_ENABLE?            [M1]
  ├─ probe_rf_setup        ─ asic_rev (PGSELECT|1, read 0xFFFE) +
  │                          detect_rf (RF probe regs 8+9)           [M2b/c]
  ├─ cold_bring_up
  │   ├─ init_hw                                                     [M2a]
  │   │   ├─ set_anaparam(rfon=True)
  │   │   ├─ INT_MASK = 0; magic 0xFE18 reset toggle (10/11/00)
  │   │   ├─ cmd_reset    (CMD |= RESET, wait <20ms; EEPROM auto-load)
  │   │   ├─ set_anaparam(rfon=True)
  │   │   ├─ RF pin defaults, CONFIG1 = 0x80, BRSR = 0x01F3
  │   │   ├─ host_usb_init (FE53 |= 0x80, RFPinsOut/Sel/En = 0x80)
  │   │   ├─ RF_TIMING = 0x000A8008, RF_PARA = 0x00100044, CONFIG3 = 0x44
  │   │   ├─ priv->rf->init  ──┐
  │   │   │                    ├─ rtl8225_rf_init   (BCD silicon)    [M2b]
  │   │   │                    └─ rtl8225z2_rf_init (z2 silicon)     [M2c]
  │   │   └─ post-RF: PGSELECT|1 magic regs (0xFFFE=0x10, TALLY_SEL=0x80)
  │   └─ start                                                       [M2a]
  │       ├─ INT_MASK = 0xFFFF; MAR[0]=MAR[1]=0xFFFFFFFF
  │       ├─ RX_CONF = 0x9094FC0B (MONITOR+MGMT+DATA+BROADCAST+NICMAC+BSSID
  │       │                        +ONLYERLPKT+AUTORESETPHY+max_fifo).
  │       │                        MONITOR (bit 0) overrides the BSSID
  │       │                        filter — without it, DATA frames
  │       │                        (incl. EAPOL) are invisible. See
  │       │                        [[feedback_station_vs_monitor_rcr]].
  │       ├─ CW_CONF (clear per-pkt CW, set per-pkt retry)
  │       ├─ TX_AGC_CTL = 0 (no per-pkt gain/antsel)
  │       ├─ TX_CONF = CW_MIN | (7<<21 max_tx_dma) | NO_ICV
  │       └─ CMD |= TX_ENABLE | RX_ENABLE     ← chip is "live" here
  ├─ probe_endpoints  ─ bulk_in=0x81, bulk_out=[0x02, 0x03]          [M3]
  └─ start RX loop    ─ async task polling bulk-IN                   [M3]
```

**M2c timing** [WIRE]: `cold_bring_up (with RF init) completed in 2.02s`
on the user's AWUS036H. Dominant cost is the 95-entry rxgain SPI loop
(190 RF writes) and the calibration sleeps (~700 ms of `msleep`).

## RF dispatch (BCD vs z2)

The "RTL8225" name covers two silicon revisions with substantially
different init tables. Both ship under the same VID:PID — we have to
probe at runtime [SRC `rtl8225.c:1025-1044`]:

```
rtl8225_write(t, 0, 0x1B7)        # arm probe
reg8 = rtl8225_read(t, 8)
reg9 = rtl8225_read(t, 9)
rtl8225_write(t, 0, 0x0B7)        # restore
if reg8 == 0x588 and reg9 == 0x700:
    return RTL8225Z2
return RTL8225 (BCD)
```

[WIRE M2b/c]: user's AWUS036H reads `reg8=0x588 reg9=0x700` → z2. The
init tables differ in:

|                 | BCD (`rtl8225_rf_init`)    | z2 (`rtl8225z2_rf_init`) |
|-----------------|----------------------------|--------------------------|
| 16-entry RF init seq | 0x067, 0xFE0, ..., 0x914 | 0x2BF, 0xEE0, ..., 0x114 |
| rxgain table    | `rtl8225bcd_rxgain` (95)   | `rtl8225z2_rxgain` (95)  |
| gain table      | `rtl8225_gain` (28)        | `rtl8225z2_gain_bg` (21) |
| sensitivity row | 2 (-82 dBm)                | 3 (-78 dBm)              |
| OFDM PHY regs   | base values                | 7 entries diverge: 0x0a, 0x0d, 0x11, 0x1b, 0x1d, 0x21, 0x23, 0x25 |
| CCK PHY 0x44–0x4b | from `rtl8225bcd` table | from `rtl8225z2_tx_power_cck[0..7]` |
| TX-power setter | `rtl8225_rf_set_tx_power`  | `rtl8225z2_rf_set_tx_power` |

`build_rf_init(t)` returns the correct callable. `set_channel` uses the
cached `RfSetup` to dispatch the per-variant TX-power refresh.

## RX descriptor (rtl8187_rx_hdr, 16 bytes, trailing)

[SRC `rtl8187.h:44-51`]

Each bulk-IN URB carries one 802.11 frame with the 16-byte trailer
appended at the end:

```
[802.11 frame (FCS-inclusive)] [rtl8187_rx_hdr (16 bytes)]
```

Trailer layout:

| Offset | Type    | Field        | Notes |
|--------|---------|--------------|-------|
| 0      | u32 LE  | flags        | bits 0..11 = frame length; 13 = CRC32 err; 20..23 = rate idx; 25 = SPLCP |
| 4      | u8      | noise        | unused by RX path |
| 5      | u8      | signal       | bit 7 = antenna A(0)/B(1) |
| 6      | u8      | agc          | used for RSSI calc |
| 7      | u8      | reserved     | |
| 8      | u64 LE  | mac_time     | TSF timestamp at frame arrival |

**RSSI formula** [SRC `dev.c:354`]:
```
rssi_dbm = -4 - ((27 * agc) >> 6)
```
Range: agc=0 → -4 dBm; agc=255 → -111 dBm. Verified [WIRE M3] across
180 frames: min=-71, max=-40, mean=-55.4 — realistic 2.4 GHz values.

**FCS handling**: `RX_INCLUDES_FCS` is on, so the frame length in the
trailer includes the 4-byte FCS. Strip it before handing the MPDU to
the parser.

## TX descriptor (rtl8187_tx_hdr, 12 bytes, prepended)

[SRC `rtl8187.h:67-72`, `dev.c:247-285`]

```
[rtl8187_tx_hdr (12 bytes)] [802.11 frame]
```

Layout:

| Offset | Type    | Field         | Notes |
|--------|---------|---------------|-------|
| 0      | u32 LE  | flags         | bits 0..11 = frame length; 15 = NO_ENC; 17 = MOREFRAG; 18 = CTS; 23 = RTS; 19..22 = RTS rate; 24..27 = data rate |
| 4      | u16 LE  | rts_duration  | only for RTS/CTS frames |
| 6      | u16 LE  | len           | **kernel writes 0** — frame length is in `flags`, this is alignment padding |
| 8      | u32 LE  | retry         | `(retry_count - 1) << 8`. Default `RETRY_COUNT=7` → `0x0600` |

**Bulk-OUT EP**: 0x02. (Device also exposes 0x03 but kernel only uses
0x02 for the L-branch; 0x03 is for the 8187B 4-queue split.)

**M5 verification** [WIRE]: 20-byte tx_hdr for a 26-byte deauth =
`1a8000000000000000060000`, decoded:
- `flags = 0x0000801a` = NO_ENC | length 26
- `rts_duration = 0`
- `len = 0`
- `retry = 0x00000600` = (7-1)<<8

20 deauths sent at 1 Mbps CCK, 0 USB errors, RX continued at 36
frames/sec in parallel.

## Channel tune

[SRC `rtl8225.c:986-1002`]

Per-channel synthesizer word from the shared `rtl8225_chan[]` table
(used by both BCD and z2):

```python
rtl8225_chan = (
    0x085c, 0x08dc, 0x095c, 0x09dc, 0x0a5c, 0x0adc, 0x0b5c,   # ch 1..7
    0x0bdc, 0x0c5c, 0x0cdc, 0x0d5c, 0x0ddc, 0x0e5c, 0x0f72,   # ch 8..14
)
```

Tune sequence (~12 register writes total, ~3 on the 8051 fast path):

1. Per-variant `set_tx_power(channel)` refresh (BCD or z2)
2. `rtl8225_write(0x7, rtl8225_chan[channel-1])` — single RF SPI write
3. `msleep(10)` for PLL lock

**M4 verification** [WIRE]: hops across 1, 6, 11, 13 deliver different
BSSID sets per channel (13/10/15/3 unique BSSIDs respectively), proving
the synth actually moves. RF7 for ch 13 = `0x0e5c` matches table
exactly.

## Warm reattach

`is_chip_warm(t)` returns True iff `CMD & (TX_ENABLE|RX_ENABLE)` — a prior
session left the MAC up + RF programmed. `connect()` then runs a bulk-IN smoke
test (3 reads); if RX is streaming it **skips the ~2 s cold init** (init_hw +
the rxgain SPI loops) and just re-arms the monitor posture via `start()`
(re-applies RX_CONF + CMD TX/RX enable, no RF work). A warm chip whose bulk-IN
pipe is wedged → "please replug" (Windows/WinUSB can't always recover it in
userland — same pattern as the rtw88 family, see [[feedback_warm_reattach]]).
`[HW]` 2026-06-11: cold then warm beacon_watch both healthy (~5 beacons/s, 0
dead seconds); the warm re-run skips the RF init and comes up near-instantly.

If you see `cmd_reset: ... never cleared (timeout)` on hw, that's
the warning sign — replug and retry.

## Faithfulness push — the road to grade A (next session)

Recon 2026-06-11. RX is already healthy (VERIFICATION.md: Scan/Handshake/PMKID/WEP
green; ~5 beacons/s, 10+ APs), so this is **completeness + soak + a WPS verdict,
NOT an RX rescue**. The driver is a real structured port (mac.py/rtl8225.py mirror
dev.c/rtl8225.c line-by-line with the kernel's named data tables — not a replay
dump), but only `init_hw` (56 of **10,096** ops) is pcap-verified. Mirror the
rt2500usb work (master 13bcf94..a3745ae).

1. **Full single-cursor verify_pcap** (today: `scripts/rtl8187/verify_pcap.py`
   covers init_hw only). Extend to init_hw → rtl8225 RF init → start() → every
   airodump/iw hop (~57). Capture is RF/PHY-dominated (RFPinsOutput 0xff80 ×1335,
   PHY[0..3] 0xff7c-7f ×1083 each) + per-hop clusters (0xff70-76, 0xff9d-9e ×~57).
   - **Blocker:** the rtl8225 RF SPI uses the 8051 fast path — `rtl8225_write_8051`
     calls `t.dev.ctrl_transfer(wValue=addr, wIndex=0x8225)`, which `rtw88_pcap_replay.
     ReplayTransport` can't replay (no `.dev`) and which `extract_ops` may filter out
     (check its wIndex handling). Either give ReplayTransport a fake `.dev.ctrl_transfer`
     that walks the same op list, or add a ctrl_transfer-level ReplayDevice to
     rtw88_pcap_replay (model on `rt2x00_pcap_replay.ReplayDevice`). Reference for a
     full Realtek walk on ReplayTransport: `scripts/rtl8188eus_dkms/verify_pcap.py`;
     for the single-cursor shape: `scripts/rt2500usb/verify_pcap.py` + `scripts/rt3070/`.
   - **Hypothesis to falsify:** `mac.start()` hand-builds RX_CONF and a comment calls
     it a "monitor-mode deviation, expected to differ on the wire." rt2500usb had the
     identical framing and it was **wrong** (the kernel's airmon filter matched ours
     byte-for-byte). Decode the capture's actual RX_CONF before assuming it deviates.
2. **Stress soak** — never run (Stress ⬜). `sweep.py --skip-baseline --longrun-min 30
   --hop-interval 0.25`, then beacon_watch RX A/B vs the kernel airodump baseline
   (`usb_dumps_new/captures_rtl8187/capture-1_logs/airodump-fixed-ch1.cap`).
3. **WPS verdict** — WPS is ❌ (PBC timeout / PIN NACKs). Likely the hard-MAC WPS gap
   (`engine/attacks/wps/README.md`): no firmware → no hardware ACK, i.e. an engine
   limitation, not a driver bug. Confirm + document; probably out of driver scope.

Captures: `usb_dumps_new/captures_rtl8187/capture-1` (+ kernel baseline), old
`usb_dumps/captures_rtl8187/capture-1..3`. Rules: hard-MAC = no firmware; 20 MHz
only; agent never fires live TX (`deauth_hw.py` pattern — wire it, user fires);

## Deferred work (post-M6)

1. **EEPROM (93cx6) bit-bang** — kernel reads MAC + per-channel TX
   power + RFKill GPIO mask from the EEPROM during probe. Wifit3 uses
   zeros for TX power (RX-only bring-up doesn't need it; see
   [[feedback_defer_efuse_on_bring_up]]). MAC is read directly from
   `MAC0..5` because the EEPROM auto-loads it into the CSR on USB
   enumeration on 8187L silicon.
2. ~~**Real warm reattach + bulk-IN smoke test**~~ — DONE 2026-06-11.
   See "Warm reattach" above (re-arm via `start()`, skip the cold RF init).
3. **8187B variant** — `rtl8187b_init_hw` is a separate code path with
   a different rx_hdr struct (`rtl8187b_rx_hdr` is 16 bytes but the
   field layout is different). Add as a second `if/else` branch in
   `mac.init_hw` when an 8187B dongle shows up.
4. **EEPROM-driven TX power for full-range injection** — at present
   we cap TX power at the table defaults. For long-range deauth
   attacks the calibrated values would matter.
5. **Cleanup**: `scripts/rtl8187/mvp.py` is the original Gemini-era
   experimental script; not imported by anything but kept in tree.
   Safe to delete in a follow-up.

## Hardware test cheat sheet

```
# M1 — control transfers + ID probe (no bring-up)
uv run python scripts/rtl8187/test_hw_rtl8187.py --phase open

# M2a — MAC bring-up only (no RF; receiver blind, FIFO primed)
uv run python scripts/rtl8187/test_hw_rtl8187.py --phase init

# M2b/c — full RF init (BCD or z2 auto-detected) + bulk-IN drain
uv run python scripts/rtl8187/test_hw_rtl8187.py --phase rf

# M3 — decode 3s of frames, print type/RSSI/BSSID stats
uv run python scripts/rtl8187/test_hw_rtl8187.py --phase rx

# M4 — hop ch 1/6/11/13, count per-channel beacons
uv run python scripts/rtl8187/test_hw_rtl8187.py --phase channel

# M5 — fire 20 broadcast deauths at the strongest ch11 BSSID
uv run python scripts/rtl8187/test_hw_rtl8187.py --phase tx

# M6 — listen for EAPOL frames on a chosen channel for ~30s
uv run python scripts/rtl8187/test_hw_rtl8187.py --phase handshake --channel 11
```

Each phase strictly supersedes the previous ones (don't chain back to
back — they all run `cold_bring_up` at the start).
