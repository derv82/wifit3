# MT7925AU

MediaTek MT7925U (Wi-Fi 7, connac3) USB driver port.

## Captured Wireless Card

- MediaTek MT7925U, dual-band (2.4 + 5 GHz), Wi-Fi 7 / connac3, USB.
- Captured unit: Netgear A9000, `VID:PID 0846:9072` (the driver also claims MediaTek
  `0e8d:7925`). USB SuperSpeed.
- Captures: `driver_captures/captures_mt7925u/` (capture-1/2/3 + per-run logs +
  `firmware/`). Recorded on Kali, kernel `6.19.14+kali-amd64`, driver `mt7925u`.

## Linux Driver Source

- Upstream: `git.kernel.org` linux-stable, tag `v6.19.14`, commit
  `b9dbb4576bc8c69e87b4ca4caa2fb1c0db47d722`; subtree
  `drivers/net/wireless/mediatek/mt76/` (mt7925-specific in `mt7925/`).
- Type: mainline. Vendored (gitignored) at `driver_sources/mt76-source-v6.19.14/` with a
  `VERSION.md` provenance marker.
- The mt792x/connac register layer is shared with mt7921; the chip-id, firmware
  container and connac3 MCU/descriptor formats are mt7925-specific.

## Python Port Details

- `VID:PID 0846:9072` + `0e8d:7925`, selected by `discovery.py` (`mt7925au`).
- Status: cold-boot bring-up is pcap-verified against all 3 captures with zero divergence
  (every host-to-device driver op reproduced; the 22 unmatched ops are OS USB enumeration,
  which no wifi driver emits). Covers firmware upload, post-boot init (`init.py`), the
  `mac_work` survey/MIB reads (`mac.py`), monitor entry, the ch 1-165 sweep
  (`config_sniffer`), the per-band TX power tables (`txpower.py`), and the world-"00"
  channel domain (`mcu.set_channel_domain`).
- RX: works on hardware, on par with a known-good card (beacon_watch A/B, both bands).
  `rx.decode_frame` decodes the connac3 RXD.
- TX (inject): `tx.build_tx` (connac3 TXWI) is byte-exact against both TX captures (573 mgmt
  frames each). Live in wifit3 on 2.4 + 5 GHz: deauth drops clients, 4-way / PMKID captured.
- Warm-reattach: reconnects without a physical replug (mt7921u_resume model). See Known
  Problems.
- Related: `mt7921au` (connac2 sibling; same mt76-USB transport, different MCU/txd).

Non-obvious in the port:

- **TX TXWI context is the monitor vif's, not defaults.** `mt7925_mac_write_txwi`'s
  per-frame fields come from the monitor link (mt7925/main.c:375-392): band_idx = `0xff`
  which `FIELD_PREP(MT_TXD1_TGID=GENMASK(13,12))` masks to **3** (TGID=3 on every frame),
  wcid = `MT792x_WTBL_RESERVED` (19), and `basic_rates_idx = MT792x_BASIC_RATES_TBL + 4`
  = **15** (TX_RATE) because the phy's default chandef lands on 5 GHz (the last band with
  world-enabled channels, mac80211.c:395-418), so main.c:382 takes the non-2.4GHz branch.
  These are constants for the monitor vif; deriving them from the inject channel is wrong.
- **connac3 txd[1] = `0x00004000`** (HDR_FORMAT_CMD at GENMASK(15,14)), not connac2's
  `0x80010000`. The single most likely mis-port when adapting from mt7921 (mcu.py).
- **MCU response header is `mt7925_mcu_rxd` (44 B)**: `rxd[8]` then len/pkt_type_id,
  so eid@36, seq@37 (connac2 was 28 B, seq@29). Used for MCU seq matching.
- **INIT_DOWNLOAD command is addr-driven**: `PATCH_START_REQ` iff addr is `0x900000`
  or `0xe0002800` (mt7925 adds the second), else `TARGET_ADDRESS_LEN_REQ`.
- **The ROM patch is AES-encrypted** (both sections): the DL_MODE comes from the
  section's `info.sec_key_idx` word (offset 20, BE) via `mcu.get_data_mode`
  (`0x80000009` for the reference patch), not a plain `NEED_RSP`.
- **epctl over the UHW bus**: `mt792xu_epctl_rst_opt` uses bRequest 0x01/0x02 on the
  Linux wire (byte-exact, no waiver). On WinUSB the UHW bus returns Errno 5, so
  `firmware._epctl_rst_opt` falls back to the unified bus.
- **`build_sku` byte order** (txpower.py): cck / ofdm(stride 40) / ht(8+8+1) / vht(4x10
  stride 12) / he(7x12) / eht(16x16) into 449 bytes. Per-channel power is binary: 0x28
  (20 dBm) on enabled 20 MHz channels, a whole-0x7f SKU on world-disabled ones
  (`get_ch_power` returns the unset tx_power=127).
- **World-"00" channel domain is a table, not a regdom port** (`mcu.set_channel_domain`):
  the per-channel `ieee80211_channel_flags` for region "00" are encoded directly
  (`constants.CHAN_*` + `mcu.W00_2G/W00_5G`), byte-identical to what any Linux region-00 box
  emits. cfg80211's regulatory engine + the reg.c world_regdom are not in the mt76 tree.
- **CLC power path is USB-disabled**: `SET_POWER_LIMIT` tag 0x3 (CLC) is never sent on USB;
  only tag 0x1 (per-band TX power) is. Don't chase the CLC path for this card.
- **Active monitor is the omac trick** (`enter_active_monitor`): program the forged MAC as
  the DEV_INFO omac and connac HW-ACKs frames with RA == that MAC; the peer bssid goes in as
  a `CONNECTION_MONITOR` BSS (under INFRA_AP a bssid switches the FW to a peer-STA context
  that kills the omac auto-ACK). No new registers, just the UNI DEV_INFO/BSS_INFO commands.
- **`build_tx` never sets NO_ACK**: the chip HW-retries an injected frame until the peer
  ACKs (up to REM_TX_COUNT=15); that HW retry is inject_frame's only retransmission, and
  active monitor is what lets the chip recognize an ACK to a forged source MAC. The
  replay-only `build_tx_no_ack` sets the bit purely to byte-match the aireplay TX capture.

## Known Problems

- **TX ctrl frames (RTS) not reproduced.** The TX captures carry 90 aireplay-injected RTS
  frames whose TXWI tid comes from `skb->priority` (mt7925_mac_write_txwi_80211), absent
  from the frame and underivable offline. wifit3 injects only the mgmt frame it is given,
  never RTS, so these stay out of scope (TX-capture only, not in the RX/monitor captures).
- **Warm reattach: hardened, Linux baseline pending.** `_warm_reattach` now mirrors the
  proven mt7921au sibling (same mt792x stack): `dma_need_reinit`-gated `_dma_init(resume=True)`
  (mt792x_dma_need_reinit / mt792xu_dma_init(resume)), a stale-EP-0x84 drain, re-post RX,
  and a best-effort GET_NIC_CAPAB with a few retries. A failed query no longer forces a
  replug: it continues MAC-less (the card stays usable). The earlier hard-replug was an
  outlier vs every other mt76 driver. Validated on Windows/WinUSB (repeated warm reconnects,
  MAC re-read, RX both bands); the WinUSB warm-pipe wedge is intermittent, and the drain +
  best-effort + retry absorb it. NOT yet baselined on Linux (no warm-open capture exists to
  byte-verify against; the changes are strictly more tolerant, so low Linux-regression risk).

## Driver Entry Points

- Firmware download: `firmware.load_firmware` (`mt7925_run_firmware` ->
  `mt792x_load_firmware` -> connac2 patch/RAM/FW_START); DMA in `firmware._dma_init`.
- Post-boot init: `init.post_boot_init` (run_firmware tail, set_eeprom, `_mac_init`).
- Monitor + channel: `mcu.uni_dev_info/uni_bss_info/set_sniffer/config_sniffer/
  set_rxfilter`; `driver.set_channel` (config_sniffer).
- Periodic reads: `mac.update_survey/update_mib_stats/reset_counters`
  (`mt792x_mac_work`).
- TX power tables: `txpower.rate_txpower_all` (`mt7925_mcu_rate_txpower_band` +
  `build_sku`); RX decode: `rx.decode_frame` (`mt7925_mac_fill_rx`).
- TX inject: `tx.build_tx` (`mt7925_mac_write_txwi` + `_write_txwi_80211`, USB SDIO
  layout from `mt7925_usb_sdio_tx_prepare_skb`); `driver._inject_frame` sends it on EP
  0x09 (HCCA); `driver._stamp_tx_seq` assigns the live 802.11 sequence.
- MCU framing: `mcu.build_mcu_frame` (`mt7925_mcu_fill_message`; 64B mcu_txd / 48B
  uni_txd, txd[1]=0x00004000).
- Register access: `transport.py` (unified bus 0x63/0x66, UHW bus 0x01/0x02).

## Scripts

- `scripts/mt7925au/verify_pcap.py`: single-cursor pcap verify (firmware +
  post_boot_init + operational dispatch), on the shared `scripts/mt76_verify_replay.py`
  engine, plus a TX BYTE-MATCH phase (auto-runs when the capture carries EP-0x09 TX
  frames). Run via `uv run python scripts/verify_pcap.py mt7925au <pcap>`.
