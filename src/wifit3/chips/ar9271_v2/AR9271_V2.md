# AR9271 v2 (`ath9k_htc`)

Clean-room re-port of the Atheros AR9271 (soft-MAC, 1T1R, 2.4 GHz only; e.g. ALFA AWUS036NHA)
from the mainline `ath9k_htc` v6.18.12 kernel source, verified op-by-op against a cold-boot pcap.
VID/PID `0x0cf3:0x9271`. Selected at runtime by `WIFIT3_AR9271=v2`; the v1 driver stays default
until v2 ties/beats it on hardware.

## Status

In progress, milestone port. **Two axes, different depths:**

- **Pcap verification** (the gate's handlers) replays byte-for-byte against all three pcaps through
  milestone **M10** — firmware download (M1), HTC/WMI handshake (M2a), the full `__ath9k_hw_init` +
  `ath9k_hw_reset` (chip reset → init_pll → ar9002 analog/initvals → RF → calibration),
  `ath9k_htc_start`, host RX init, and the channel-hop sweep. As of 2026-06-25 the gate reproduces
  ~1131 of ~8860 host ops; **frontier = the first fast channel change (`do_fastcc`)**, an int-OUT
  `0x04`. Run: `uv run python scripts/verify_pcap.py ar9271_v2`.
- **Live driver wiring** is still early: `connect()` raises after the handshake (M2a), and
  `set_channel`/`inject_frame` are stubs. The M3–M10 logic lives in the chip modules (`hw.py`,
  `calib.py`, `phy*.py`, `chan.py`, `rx.py`, …) and is driven by the gate, **not yet wired into
  `connect()`**. Nothing hardware-tested.

## Gotchas

**This port runs the mainline `htc_9271-1.4.0.fw`, not v1's "cleanroom" firmware.** The v1 driver
(`chips/ar9271/`) decoded a different firmware whose event IDs, RX header layout, and HIF tags
diverge from mainline ath9k_htc — so v1's protocol notes do not transfer here, and v2 is a fresh
bring-up against the *kernel's own* wire protocol, not a port of v1. Do not cross-reference v1.

**Firmware download keeps the USB device address across re-enumeration** on the Linux capture
(devnum unchanged after the `0x31` complete write), so the verify harness demuxes one devnum for
both cold and warm phases. Don't assume a devnum change marks the boot boundary.

## Orientation

Soft-MAC: the firmware runs HTC/WMI; the host downloads it then drives PHY/MAC over WMI. Cold
boot streams the blob into RAM in 4096-byte vendor control writes (`bRequest 0x30`, load address
in `wValue>>8`) then a `0x31` "jump to text" write — `firmware.download`, ported from
`ath9k_hif_usb_download_fw` ([SRC] hif_usb.c:1068). Four pipes: bulk-OUT `0x01` (TX/HTC), bulk-IN
`0x82` (RX), int-IN `0x83` / int-OUT `0x04` (WMI/HTC ctrl) — [SRC] hif_usb.h:69-72.

Source: `data_dumps/ath9k-source-v6.18.12/` (`hif_usb.c`, `htc_hst.c`, `wmi.c`, `htc_drv_*.c`,
`hw.c`, `mac.c`) — Linux stable v6.18.12, the capture's own kernel; see its `VERSION.md`.
Capture bundle: `usb_dumps_new2/captures_ath9k_htc_newddevice/`.

## Scripts

- `scripts/verify_pcap.py ar9271_v2 [capture-1|2|3]` — strict single-cursor replay gate.
- `scripts/ar9271_v2/ar9271_pcap_replay.py` — the pcapng extractor + ReplayDevice it drives.

## Debug log

### 2026-06-25 — v2 re-port kicked off

v1 was one of the first ports, done before the verify-against-pcap process; it shipped a 2-channel
channel-tune stub for weeks and a new card heard only ~2 APs across all channels. Started a blind
re-port from the v6.18 kernel C against a fresh cold-boot capture. M1 firmware download matched the
wire on all three pcaps; frontier sits at the first HTC/WMI handshake op (int-OUT `0x04`).

### 2026-06-25 — M3 init_cal (calibration), op469→520

`ar9002_hw_init_cal` (`calib.py`): cl_cal carrier-leak → ar9271 pa_cal → loadnf → start_nfcal →
IQ-cal setup. All matched on all three pcaps. Notes:

- **Only the IQ-mismatch cal is armed.** ADC-gain/ADC-dc are HT40-only (`ar9002_hw_is_cal_supported`),
  and the bring-up channel is legacy-20, so cl_cal also skips its parallel-cal (HT20) branch.
- **`ar9271_hw_pa_cal`'s pre-loop buffer emits only 10 RMWs on the wire, not the v6.18 source's 15.**
  The capture's firmware revision omits the last 5 (RF2G1 PDPADRV2/PDPAOUT clear + RF2G8/RF2G7
  PADRVGN2TAB0 + RF2G3 CCOMP field writes) — all on registers the function snapshots up front and
  restores at its tail, so dropping them is wire-visible but functionally inert. The port matches the
  wire (10 ops); see the NOTE in `calib.pa_cal`.
- NF load is feedback-shaped: cold (no caldata) → chain-0 nfval is the band nominal (−118), then the
  −50 maxCCApower restore; the AGC/NF wait loops terminate on the replay's recorded busy-bit clears.

### 2026-06-25 — M4 ath9k_hw_reset tail, op520→522

`hw.reset_tail` closes out `ath9k_hw_reset`: the saved LED state OR 32 kHz sleep clock (`AR_CFG_LED`),
then the AR9271 USB descriptor byte-swap (`init_desc` → `AR_CFG = SWRB|SWTB`). `restore_chainmask`
(ar9003-only private op), `gen_timer_start_tsf2` (no tsf2 timer), and `apply_gpio_override`
(`gpio_mask` 0) all collapse to no-ops here, so the tail is just two writes. Frontier moves to the
post-reset htc-start (txpower update + `WMI_SET_MODE`/`ATH_INIT`/`START_RECV`).

### 2026-06-25 — M5 htc-start tail, op522→528

`ath9k_htc_start` after the reset returns: `ath9k_cmn_update_txpow` then `SET_MODE`/`ATH_INIT`/
`START_RECV`. `priv->txpowlimit` is **0** at the first start, and `reg->power_limit` was the
`MAX_COMBINED_POWER` init default, so the guard fires and `ath9k_hw_set_txpowerlimit(0)` re-runs
the tx-power path with `new_pwr = 0` — clamping every per-rate target to 0 (`0x0a` after the +10
table offset; cf. `phy_power.update_txpow`). The gain config + 32-word PDADC table are
limit-independent and reproduce the reset-time `apply_txpower` byte-for-byte; only the six per-rate
registers change. Then `WMI_SET_MODE` carries `HTC_MODE_11NG` (be16 `0x0001`); `ATH_INIT` and
`START_RECV` are empty. Frontier moves to the RX path (`ath9k_host_rx_init` / cap-target update).

### 2026-06-25 — M6 host_rx_init + cap-target, op528→541

`rx.host_rx_init`: `rxena` (`AR_CR = RXE`), `opmode_init` (STA `calcrxfilter` → `0x207`
ucast|mcast|bcast|mybeacon; `setrxfilter` clears `AR_RXCFG` ZLFDMA since no phy-err bits;
`setmcastfilter` = all-ones), then `startpcureceive` (`enable_mib_counters`, `ani_reset`, clear
`AR_DIAG_SW` RX-block/abort). `calcrxfilter` first *reads* `AR_RX_FILTER`/`AR_PHY_ERR`
(`getrxfilter`) to preserve phy-err bits — those are the two reads ahead of the filter write.

`ani_reset`'s `set_ofdm_nil`/`set_cck_nil` issue **no** register writes on cold STA bring-up: the
immunity levels resolve to the defaults and the INI-cached ANI state already matches the
default-level table, so only `ani_restart` reaches the wire (the gate confirms this). Then
`WMI_TARGET_IC_UPDATE` pushes the 8-byte cap struct (ampdu 0xffff / 0xff subframes / coex 0 /
tx-chainmask 1). Frontier moves to the channel-config / tune sweep.

### 2026-06-25 — source reference re-pinned to authoritative v6.18.12

The local `data_dumps/ath9k-source-v6.18/` turned out not to be a clean kernel checkout of any
tag — a transformed/standalone snapshot (`kzalloc_obj()` macro, no `usb_get_dev`/`usb_put_dev`,
`module_init` stubs in `common.c`), matching neither mainline v6.18.0 (what the web-container
agent pulled) nor the capture kernel. Re-pulled the exact `drivers/net/wireless/ath/ath9k/` from
git.kernel.org linux-stable **v6.18.12** (= the capture's `6.18.12+kali-amd64`) into
`data_dumps/ath9k-source-v6.18.12/` and re-pointed all citations there. 13/112 files differed
between the trees; the 7 the port cites differ **only** in host-side allocation/refcount/module
plumbing — zero USB-wire bytes, so no milestone changed and the gate result is unaffected (it
reads the port + pcap, not the source). The frontier code (`do_fastcc`/`ath9k_hw_reset` in
`hw.c`) is byte-identical across the trees. Also fixed the gate's capture path
(`usb_dumps_new` → `usb_dumps_new2`), which the web container's layout had pointed elsewhere.
