# AR9271 v2 (`ath9k_htc`)

Clean-room re-port of the Atheros AR9271 (soft-MAC, 1T1R, 2.4 GHz only; e.g. ALFA AWUS036NHA)
from the mainline `ath9k_htc` v6.18.12 kernel source, verified op-by-op against a cold-boot pcap.
VID/PID `0x0cf3:0x9271`. This is now the **default** AR9271 driver; `WIFIT3_AR9271=v1` falls back
to the original v1 driver.

## Status

In progress, milestone port. **Two axes, different depths:**

- **Pcap verification** (the gate's handlers) replays byte-for-byte against all three pcaps through
  the whole **cold boot + the entire operational channel sweep + the aireplay-ng TX/injection
  phases** — firmware download, HTC/WMI handshake, `__ath9k_hw_init` + `ath9k_hw_reset`,
  `ath9k_htc_start`, host RX init, the full + fast (`do_fastcc`) channel changes, the airodump
  band-hop, the `iw set channel` sweep, and the aireplay-ng `--test` + deauth bulk-OUT frames. As
  of 2026-06-25 the gate **PASSes all three** (8861/8867/8866 host ops); the LED-blink timer's
  interleaved GPIO writes are reproduced via the real `set_gpio` (seq-aligned), the lone ch14
  per-rate-power op is a named value-exception (host cfg80211 regulatory), and 2/4/0 TX cookies are
  a named cookie-exception (the TX-slot allocation race; see the debug log). Run:
  `uv run python scripts/porting/verify_pcap.py ar9271_v2`.
- **Live driver wiring is converged** (the 8821cu shape). The cold boot + channel-hop
  orchestration now lives in the driver: `bringup.cold_bringup()` (firmware-booted → monitor
  receiver on ch1) and `bringup.full_channel_change`/`fast_channel_change`, driven by the public
  `driver.connect()` / `driver.set_channel(ch)`. The gate builds `AR9271V2Driver` over the
  ReplayDevice transport and calls **those public methods** (`connect`, `set_channel`,
  `inject_frame`) — one cursor, no per-leaf harness — and still PASSes all three (8861/8867/8866).
  `connect`/`set_channel` are dual-mode: no running loop → inline (the gate); under the app's loop
  → executor-offloaded with the bulk-IN `RxReaderThread` started first. Live RX delivery is wired
  (`rx_decode.iter_frames` → `WlanFrameParser` → callback). `inject_frame` stays synchronous (gate
  + unit tests); the async UI wrapper the deauth path awaits is the one remaining TX step (live
  firing = the user's gate).
- **Hardware-validated — cold bring-up, RX, hopping, AND warm reattach.** On a cold (fresh-plug)
  card the full live path runs: firmware download → re-enumerate → claim interface 0 →
  `cold_bringup` → monitor on ch1, then ~8 beacons/s from the best AP (~82% of the 9.77/s wire
  ceiling), 10+ APs, zero dead seconds. Multi-channel hopping confirmed live (ch1/6/11). On a
  **warm** card (firmware already running from a prior session), `connect()` light-reattaches with
  **no replug, no re-download** (`bringup.warm_reattach`): RX resumes immediately and `set_channel`
  hops work. Both paths via `scripts/diag/beacon_watch.py` / `scripts/chips/ar9271_v2/test_hw.py`
  (`--no-reset` exercises the warm path).

## Gotchas

**This port runs the mainline `htc_9271-1.4.0.fw`, not v1's "cleanroom" firmware.** The v1 driver
(`chips/ar9271/`) decoded a different firmware whose event IDs, RX header layout, and HIF tags
diverge from mainline ath9k_htc — so v1's protocol notes do not transfer here, and v2 is a fresh
bring-up against the *kernel's own* wire protocol, not a port of v1. Do not cross-reference v1.

**Firmware download keeps the USB device address across re-enumeration** on the Linux capture
(devnum unchanged after the `0x31` complete write), so the verify harness demuxes one devnum for
both cold and warm phases. Don't assume a devnum change marks the boot boundary.

## Orientation

Soft-MAC: the firmware runs HTC/WMI; the host downloads it then drives PHY/MAC over WMI. Cold
boot streams the blob into RAM in 4096-byte vendor control writes (`bRequest 0x30`, load address
in `wValue>>8`) then a `0x31` "jump to text" write — `firmware.download`, ported from
`ath9k_hif_usb_download_fw` ([SRC] hif_usb.c:1068). Four pipes: bulk-OUT `0x01` (TX/HTC), bulk-IN
`0x82` (RX), int-IN `0x83` / int-OUT `0x04` (WMI/HTC ctrl) — [SRC] hif_usb.h:69-72.

Source: `driver_sources/ath9k-source-v6.18.12/` (`hif_usb.c`, `htc_hst.c`, `wmi.c`, `htc_drv_*.c`,
`hw.c`, `mac.c`) — Linux stable v6.18.12, the capture's own kernel; see its `VERSION.md`.
Capture bundle: `driver_captures/captures_ath9k_htc_newddevice/`.

## EEPROM variants (any-card support)

The AR9271 is effectively a **single-config 1T1R 2.4 GHz part**: the 4k EEPROM (`base_eep_header_4k`
+ `modal_eep_4k_header`) is mostly **calibration VALUES** (piers, PDADC, CTL edges, ant-ctrl,
iq-cal, ob/db, macaddr) already consumed by computation — so any burn works without a branch. The
reference card (all three captures) reads: **txGainType 0 (normal-power), modal-header v4,
eeprom-rev 0xf, bb_desired_scale 0, spurChans[0]=AR_NO_SPUR, tx/rx-mask 1/1**. `connect()` logs
this line once (`ar9271_v2 EEPROM config: …`) so an odd card is diagnosable at a glance.

The genuinely EEPROM-*branched* init, all runtime-gated (the reference wire is byte-unchanged — see
`verify_pcap`):

- **txGainType → TX-gain INI table** (`phy.process_ini`, `ar9271_hw_init_txgain_ini`
  [SRC] ar9002_hw.c:144): `MODES_NORMAL_POWER_TX_GAIN_9271` vs `MODES_HIGH_POWER_TX_GAIN_9271`
  (both ported 1:1). **This is the one discriminator that genuinely varies across real AR9271
  cards** (high-power designs burn txGainType=1). The high-power path is hardware-untested (the
  reference is normal-power) but pcap-selected off the same runtime read. Note AR9271 has **no
  rxGainType branch** — `ar9280_20_hw_init_rxgain_ini` gates on `AR_SREV_9280_20`, not 9271; RX gain
  is baked into the main `iniModes` table.
- **modal-header version → ob/db remap** (`phy_board._ob_db_by_version`
  [SRC] eeprom_4k.c:826-859): v≥2 takes the five distinct nibbles as decoded; v1 replicates the
  [1] nibble; v0 replicates [0] (with db2←db1_0, the kernel quirk). AR9271 consumes only
  ob[0..2]+db1[0]+db2[0], so v0/v1 only move ob[2] and (v0) db2[0]. Ported; hardware-untested (all
  known AR9271 EEPROMs are v3/v4).
- **txGainType==0 & bb_desired_scale≠0 → smart-antenna TX-pwrctrl block**
  (`phy_board._apply_bb_desired_scale` [SRC] eeprom_4k.c:1007): 6 packed `AR_PHY_*_TX_PWRCTRL`
  RMWs. Ported; inert on the reference (bb_desired_scale=0).

### Residual gap (documented, not ported)

- **In-band 2 GHz spur mitigation** (`phy.spur_mitigate`; `ar9002_hw_spur_mitigate` tail +
  `ar5008_hw_cmn_spur_mitigate`, ~24 further PHY regs). The reference — and every AR9271 4k EEPROM
  seen — has `spurChans[0]=AR_NO_SPUR`, so this path has **no wire to verify against**; it stays a
  clear `NotImplementedError("untested variant: in-band 2 GHz spur …")` rather than an unverifiable
  1:1 port. A card with a populated 2 GHz spur table would need it ported (spur-programming is the
  only unported EEPROM-reachable branch).

`do_fastcc` (`ath9k_hw_do_fastcc` → `ath9k_hw_channel_change`): check_alive, the 10-QCU

### 2026-06-25 — frontier: ch14 OFDM/HT power (host regulatory, not wire-derivable)

The walk stops at the airodump hop to **ch14** (2484 MHz) — identically in all three pcaps. The
per-rate write reduces OFDM + HT20 by exactly 2 (1 dB) while leaving CCK at 36: wire OFDM=0x26
(38) / HT20=0x24 (36), port computes 0x28 (40) / 0x26 (38). pcap_slicer maps the divergent frame
to the `AIRODUMP --band abg 250ms hop` phase (the apply_txpower precedes rf_set_freq in the reset
body, so the ch14 synth lands a few ops later — the channel-tracking is what made it look like a
one-off ch1 blip earlier). The kernel's `ath9k_hw_4k_set_txpower` (read in full) produces
*identical* output for ch1 and ch14 for every `cfgCtl`/`powerLimit`/`antenna_reduction` — the
eeprom OFDM/CCK piers and CTL edges at 2484 don't bind (edges ≥ 40). The OFDM−2/HT−2/CCK−0 split
isn't a clamp (a clamp would hit CCK or give equal values); it's the cfg80211 ch14 OFDM
regulatory restriction (Japan-only / `NO_OFDM`), host state with no USB-wire or eeprom signature.
Open: model the regulatory ch14 limit vs. a named per-rate value-exception. NOT waived — awaiting
a call.

__be16 payload_len][tx_mgmt_hdr | tx_frame_hdr][802.11]`. The `--test` run sends broadcast + SSID
probe requests on the mgmt endpoint (epid 5, `tx_mgmt_hdr` 8B: node/vif/tid/flags/key_type/

### 2026-06-25 — M12 inject_frame ported; all three pcaps PASS

`driver.inject_frame` builds the full TX wrapper around the 802.11 frame and bulk-OUTs it:
classify by frame type (`ieee80211_is_data` → BE data endpoint / `tx_frame_hdr` 12 B; mgmt +
control → mgmt endpoint / `tx_mgmt_hdr` 8 B [SRC] htc_drv_txrx.c:381/:260/:214), allocate the
TX-slot cookie (`tx.TxSlots` = `ath9k_htc_tx_get_slot`'s `find_first_zero_bit` over a 256-bit
bitmap [SRC] :79), fill the header (node/vif/tid/flags 0, key CLEAR, keyix INVALID), wrap. Endpoints
come from the handshake service map (`WMI_MGMT_SVC` → 5, `WMI_DATA_BE_SVC` → 6 here), not hardcoded.

**Cookie = a TX slot, freed on completion — modelled, then proven equivalent to the simpler form.**
`ath9k_htc_txstatus` [SRC] :647 frees a slot when its `WMI_TXSTATUS` event arrives, *gated* on the
frame's skb already being queued by the bulk-OUT URB completion (else the event waits in
`pending_tx_events` for the 50 ms cleanup timer). I validated both the URB-gated two-stage model and
the simpler "free at the txstatus event" model offline against all three pcaps: **identical** results
(the status always trails its own URB on the wire), so the port frees immediately. The gate feeds the
recorded `WMI_TXSTATUS` events to `driver.tx_status_event`, interleaved by capture frame number.

**The TX-slot allocation order is a host-scheduling race (named cookie-exception, 2/4/0).** This
model reproduces **747 of 753 inject cookies byte-exact**; the 6 residue (capture-1 = 2, capture-2 =
4, capture-3 = 0) are frames where the cookie (= allocation order) inverts vs. the USB-transmit order
— mac80211 queue servicing racing the `wmi_event` tasklet with up to ~35 frames in flight, with no
signal in the 802.11 frame the gate hands `inject_frame`. URB-gating + the 50 ms timer does not fix
them (confirmed). Per the lead's call these are a *named, byte-precise, counted* cookie-exception
(`ReplayDevice._cookie_excepted`): a TX bulk-OUT frame may differ from the wire **only** in the single
cookie byte (mgmt off 18 / data off 22) with every other byte matching — the same host-state-exception
philosophy as the 33 TSF and 1 ch14 value-exceptions. Result: **PASS on all three** (8861/8867/8866),
33 TSF + 1 ch14 + 2/4/0 cookie exceptions, 20/16/20 reproduced LED blinks. Unit tests in
`tests/chips/ar9271_v2/test_tx.py`.

### 2026-06-26 — HW-validated on a cold card; warm re-download instability found

Live bring-up works end-to-end on a fresh-plug (cold) card: `beacon_watch.py` brought the card up
through `driver.connect()` (firmware → re-enumerate → claim if 0 → `cold_bringup`) to monitor on ch1
and tallied **1346 beacons in 25 s, mean 8/s from the best AP (~82% of the 9.77/s ceiling), 10+ APs,
zero dead seconds** — healthy RX, and a big jump over v1 (which heard ~2 APs across all channels).
Two live-path fixes were needed (none touch the gate's inline path): claim interface 0 after
re-enumeration (bulk/interrupt pipes need it; EP0 control — the FW download — does not, which is
why that part succeeded first); tolerate the transient `[Errno 13]` while Windows re-binds WinUSB
(retry the claim through the settle); swallow `USBTimeoutError` in the bulk-IN reader (no traffic is
benign, not a fatal error); dispose the cold handle before re-enumeration.

Found the warm-state limitation: a SECOND `connect()` without a replug re-downloads firmware to a
card already running it, which re-enumerates the device mid-handshake → `[Errno 19] No such device`,
and it then drops off the bus until physically replugged. `test_hw.py` sidesteps this with a USB
`reset()` before bring-up (the programmatic replug). The production fix is a warm-reattach path
(`is_chip_warm()` → skip download → smoke-test the bulk-IN pipe), the 8821au pattern — the next
milestone. Multi-channel HW hop confirm is also pending (pcap-proven for the whole ch1–12 sweep).

### 2026-06-26 — warm reattach working (no replug); cold/warm both HW-validated

Multi-channel hopping confirmed on a cold card (ch1/6/11, 1555 frames). Then ported a true
**warm light-reattach** (`bringup.warm_reattach`), taking the clue from the **v1** driver's warm
path — for warm USB lifecycle, not the wire protocol (the blind re-port stands). Keys:

- **Skip the handshake, reconstruct the endpoint map.** The one-shot HTC_READY only fires at
  firmware boot, so the cold handshake can't re-run on a warm card. But the firmware assigns HTC
  endpoints sequentially in `SERVICE_CONNECT_ORDER` (verified off the capture: CONTROL=1, MGMT=5,
  DATA_BE=6, credits 33), so the map is reconstructable as `{svc: i+1}`.
- **Reuse the running firmware; repopulate host shadows READ-ONLY.** The chip's MAC/PHY is already
  configured (monitor mode, RX streaming), so only the `AthHw` shadows are rebuilt — `read_revisions`
  (SREV) + `eeprom.init` (4k map → macaddr + chain masks) + `init_tx_queues` (alloc) — exactly what
  `set_channel`'s computed reset needs. No download, no destructive reset, so a failed reattach
  can't bork the card (it just times out → fall back to a replug prompt) and is freely retryable.
- **Toggle resync.** `clear_halt` is often ignored by the AR9271, so the first WMI command after
  re-attach is dropped on an OUT-pipe data-toggle mismatch (device ACKs it as a duplicate → no
  response → read timeout). Resending advances the host toggle until it matches; `warm_reattach`
  retries the idempotent SREV read up to 8× (v1's `send_wmi_command` resend trick). Without this the
  reattach was ~50/50 (toggle parity); with it, reliable across repeated runs.

Detection is the bulk-IN smoke test (`_is_chip_warm`): a warm card streams HIF-framed RX (tag
0x4e00) on 0x82, a cold bootloader is silent there. `connect()` now: probe → warm? light-reattach
(fall back to replug on failure) : cold boot. Validated live — warm reattach + ch1/11/6 hops, RX
healthy, repeatable with no replug between runs. (A USB `reset()` does NOT cold-boot this chip — the
RAM firmware survives — so reset-to-cold was a dead end; reattach is the right answer.)

### 2026-06-26 — warm-reattach hop wedge: it was a POWER_ON (RTC) reset killing live firmware

The committed warm reattach delivered RX but `set_channel` on a warm card was flaky — often the
firmware went **silent partway through the hop and RX died** ("a few beacons then silence"), and a
pending WMI read then timed out on quit. Long hunt down two wrong trails (a continuous REG_IN
"drainer" — premised on WMI events flooding 0x83, but a counter showed **zero** events; and an
"idle gap before the first reset" timing theory — disproved when an *inline* first reset failed
while test_hw's small-gap one worked). The hop-op counters pinned it: the firmware went silent
exactly at the chip reset inside `reset_begin`.

Root cause: a fresh `AthHw` has `reset_power_on=False`, which makes `set_reset_reg` force a full
**POWER_ON reset** — `set_reset_power_on()` writes `AR_RTC_RESET`, resetting the RTC/clock domain
the *running firmware* lives on, wedging it. Cold sets `reset_power_on=True` after its initial
power-on, so cold hops take `set_reset()` (writes only `AR_RTC_RC` — a MAC-only reset the firmware
survives). The warm chip was already power-on-reset at firmware boot, so the host shadow should say
so. Fix (`warm_reattach`): `hw.reset_power_on = True` (+ `htc_reset_init = False`, skipping the
one-shot RF-reset pulse cold hops also skip). Warm `set_channel` now does the same MAC-only reset
as cold → reliable. Validated: warm reattach → idle → 5 hops all OK, RX healthy on each, repeatable.
(The "drainer" experiment was reverted — there are no 0x83 events to drain on this firmware.)

### 2026-07-11 — generalized to any AR9271 EEPROM (removed two fail-loud guards)

Audited every EEPROM-derived branch for hardcoding to the captured board (see the new **EEPROM
variants** section). Finding: **AR9271 is one config — the only discriminator that genuinely varies
across real cards, txGainType (normal vs high power), was already runtime-gated** and both TX-gain
tables are ported 1:1. The rest of the EEPROM is calibration VALUES, already consumed by
computation. Decoded all three captures' maps to ground-truth the reference discriminators
(identical: normal-power / modal v4 / rev 0xf / bb_scale 0 / no in-band spur / mask 1/1).

Converted the two cheap-to-port fail-loud `NotImplementedError` guards in `set_board_values` into
runtime-gated 1:1 ports so a foreign EEPROM "gives it a shot" as the kernel would: the modal-header
**ob/db version remap** (v0/v1 vs v≥2, `_ob_db_by_version`) and the **txGainType==0 bb_desired_scale
TX-pwrctrl block** (`_apply_bb_desired_scale`, +6 `AR_PHY_*_TX_PWRCTRL` regs in `reg.py`). Both are
inert on the reference (v4, bb_scale 0), so the gate is byte-identical: **PASS 8861/8867/8866**,
same exceptions as before. Added `driver._log_detected_config` (one line at connect) and unit tests
for both branches (`tests/chips/ar9271_v2/test_board_variants.py`, 8 cases). The **in-band 2 GHz
spur** block stays a documented residual (no wire to verify; reference spurChans[0]=AR_NO_SPUR) with
a clear "untested variant" message. All changes are confined to `chips/ar9271_v2/`.
